# Aura AQ: ревью AP-настройки и HTTP-обрывов, 2026-11-01

**В 1.2.1-beta-1625a09 остаются дефекты в связанном коде. Причина случаев Chris и #158 не установлена.** После независимого ревью подтверждена пропущенная P1-регрессия повторного закрытия HTTP-сессии и порча UTF-8 SSID; F2 понижена до латентной P3. [Сравнение, повторные проверки и актуальный порядок исправлений](HTTP_AP_REVIEW_COMPARISON_20261101.md). Ниже сохранены шесть первоначальных findings с коррекцией F2; исходная редакция сохранена в evidence. Положительные отзывы пользователей 1.2.1 не опровергают ошибки, которым нужны конкретные условия.

## Подтверждённые findings

### F1 — P2: ошибка выделения памяти превращается в пустой HTTP 200

Файлы: `src/web/WebPortalHandlers.cpp:85`, `src/web/WebWifiPage.cpp:25–51,83–89`; отправка `src/web/WebResponseUtils.cpp:174`.

Шаблон копируется в Arduino String, затем копируется/пересобирается при заменах. Возвраты выделения памяти и полнота HTML не проверяются. Настоящий Arduino String при отказе copy/reserve может стать пустым; handler безусловно вызывает sendHtmlStream с кодом 200. Для пустого тела потоковый helper корректно завершит пустой ответ и посчитает его успешным — он не знает, что здесь должна быть форма.

**Воспроизведение:** с текущими неизменёнными функциями handler/render и реальным `WString.cpp/.h` Arduino 3.3.12 нормальная страница содержит 24 410 байт; инъекция отказа первой либо второй большой String-аллокации даёт `HTTP 200`, ноль байт HTML. Сетевой sender в этом стенде заменён сборщиком ответа; failure semantics String настоящие. Память ESP32 и частота реальной нехватки памяти не эмулировались. Обычные native-тесты используют std::string и эту ветвь не покрывают.

**Версии/связь:** прикладная цепочка без этих проверок присутствует в 1.2.0, 2dddfa2 и 1625a09. Fault injection выполнена на текущем Arduino, а не на старой бинарной 1.2.0. Может дать именно пустую страницу Chris, если была нехватка памяти; такого факта у него нет. Сам по себе этот сценарий не создаёт `HTML stream interrupted`. Для #158, где отправляется готовый PROGMEM gzip, этот путь генерации не подходит.

**Исправление:** явный результат рендера с контролем копирования/reserve/concat; при ошибке небольшой статический 503 и запись стадии подготовки. Не отправлять пустую/усечённую форму как успех. Уменьшение копий — отдельно после измерений; не объявлять нехватку PSRAM установленной причиной.

### F2 — P3 после сравнения: латентная гонка Wi-Fi power save guard

Файл: `src/core/WifiPowerSaveGuard.cpp:14–16,34–51,60–70`; потребители `src/modules/MqttManager.cpp:1341` и `src/web/WebResponseUtils.cpp:188,214`.

Глобальные depth/previous mode используются без синхронизации из network-task и HTTP-task. Оба task могут вытеснять друг друга даже на одном core. Проверка WebHandlersShouldPauseMqttConnect выполняется до connectClient и не исключает уже начавшееся подключение.

**Воспроизведение:** реальный WifiPowerSaveGuard, SDK-вызовы заменены детерминированным планировщиком. Первый restore уменьшает depth до нуля и готовится восстановить MIN_MODEM; перед применением режима второй task успевает suspend при ещё выключенном PS и увеличивает depth. Старый restore затем включает MIN_MODEM при активном втором guard. Контрольный последовательный сценарий восстанавливает режим правильно.

**Версии/связь — исправлено после независимого ревью:** файл одинаков в stable/ранней beta/текущей beta. Гонка учёта владельцев подтверждена, но production NetworkManager задаёт `WIFI_PS_NONE` (`src/modules/NetworkManager.cpp:53`). Стенд начинает с `MIN_MODEM`; он не доказывает включение PS или влияние на HTTP в штатной конфигурации. Первоначальная P2 и предложение считать это кандидатом причины #158 были завышены. Приоритет P3; фактическая частота и влияние на устройство неизвестны.

**Исправление:** сериализовать весь переход режима и учёт владельцев одним механизмом, рассчитанным на блокирующие Wi-Fi API; одного atomic-счётчика недостаточно. Проверить также внешние вызовы set_ps при STA connect/OTA. Не держать spinlock вокруг блокирующего SDK-вызова.

### F3 — P2: query у корневого адреса обходится без Wi-Fi setup

Файл: `src/web/WebDashboardPage.cpp:11–18`, вызывающий `WebPortalHandlers.cpp:97–100`, `WebTransportEspHttpServer.cpp:553`.

IDF маршрутизирует по URL path, но request.uri возвращает строку вместе с query. В AP режиме классификатор проверяет только `uri == "/"`. Поэтому `/` показывает настройку, а `/?cache=123` попадает в dashboard. `/dashboard` в AP разрешён отдельно намеренно, что подтверждено существующим тестом; проблема относится к query у `/`.

**Воспроизведение:** с production WebDashboardPage.cpp: `/` → WifiPortal; `/?cache=123` → Dashboard. SDK `httpd_uri.c` подтверждает выбор обработчика по UF_PATH, так что вызов корневого handler с query достижим.

**Версии/связь:** одинаково в 1.2.0, 2dddfa2, 1625a09. Может показать не ту страницу настройки при URL с параметрами; не объясняет обрыв передачи или пустой браузер без дополнительного условия. У Chris URL неизвестен; в #158 речь об обычном STA dashboard.

**Исправление:** нормализовать path перед выбором root action. Проверить `/`, `/?`, `/?x=1`, `/dashboard`, `/wifi`, AP и STA, не ломая разбор аргументов.

### F4 — P2: Rescan возвращает состояние до запуска нового сканирования

Файл: `src/web/WebPortalHandlers.cpp:56,71–86`; JS `src/web/WebTemplates.h:501–535`; очередь `src/modules/NetworkManager.cpp:217`.

После предыдущего завершённого scan снимок содержит false и старые сети. `/wifi?scan=1` берёт этот снимок, ставит новую команду в очередь, затем рендерит тот же false/старый список. JS запускает polling только если scanInProgress true. Новый scan проходит в фоне, но его результат не подхватывается страницей.

**Воспроизведение:** извлечена без изменения реальная handleWifiRoot; даже callback, мгновенно меняющий живое состояние на scanning, не меняет уже скопированный snapshot. Итог: одна команда scan, реальное состояние true, HTML содержит `var scanInProgress = 0;` и старые сети. Контрольный следующий GET во время scan рендерит 1. Извлечённая функция побайтно совпадает с v1.2.0.

**Версии/связь:** все три сравниваемые версии. Подтверждённый дефект настройки, но он требует нажатия Rescan; не объясняет первое открытие пустой страницы Chris и не связан напрямую с #158.

**Исправление:** явно подтверждать принятие нового scan и отслеживать его поколение/завершение. Простое повторное snapshot сразу после enqueue тоже подвержено задержке очереди. Проверить rejection/OTA busy, уже идущий scan, пустой список и позднее выполнение команды.

### F5 — P2, статический проход: stopScan не останавливает драйверное сканирование

Файл: `src/modules/NetworkManager.cpp:767–774`; SDK wrapper `managed_components/espressif__arduino-esp32/libraries/WiFi/src/WiFiScan.cpp`, функции scanDelete и _scanDone.

stopScan вызывает только WiFi.scanDelete и сбрасывает прикладные flags. scanDelete очищает flags/результаты Arduino, но не вызывает esp_wifi_scan_stop. Если scan был активен, он может продолжаться после объявленной остановки; последующий _scanDone игнорируется из-за снятого WIFI_SCANNING_BIT. Потенциально пропускается и чтение/освобождение списка AP SDK. Сколько памяти удерживается и как долго — здесь не измерялось; бесконечная утечка не заявляется.

Вызовы есть при OTA busy и timeout scan. В прикладном коде stopScan одинаков по поведению в stable/beta; контракт wrapper проверен на текущем Arduino. Это дефект отмены, но для первого посещения AP без отмены он не является объяснением. [SDK отдельно предоставляет остановку scan и освобождение списка](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/network/esp_wifi.html).

**Исправление:** настоящий stop с обработкой результата, согласованием завершающего события и освобождением результатов. Проверить отмену в процессе scan и повторный scan, а не только сброс прикладного bool.

### F6 — P2, статический проход: ошибка обычного HTTP send теряется

Файл: `src/web/WebTransportEspHttpServer.cpp:578–607,1258–1282,1285–1307`.

Для non-stream ответов результат httpd_resp_send игнорируется. Ошибка не передаётся dispatch и не вызывает stopClient; оба dispatch завершаются ESP_OK. После частичной отправки и recoverable socket timeout сервер может оставить сессию, хотя Content-Length/framing уже не завершены. Для обычного peer RST сам сокет тоже перестанет работать, но это не заменяет обработку всех ошибок.

Затрагивает 302 captive redirect, JSON scan_status, API/диагностику. Новая история recent_failures охватывает потоковые ответы, поэтому такой сбой туда не попадает. SDK log может сохраниться. По [контракту HTTP server](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/protocols/esp_http_server.html) handler возвращает ошибку для закрытия неуспешной сессии. SDK httpd_sess_process отслеживает этот возврат, а не спрятанный в нашей обёртке результат send.

Поведение есть в 1.2.0 и 1625a09. Это дефект обработки уже случившегося сбоя, не доказанная инициирующая причина #158; его HTML идёт через другой, исправленный streaming path. Полный keep-alive/session сценарий на ESP32 в этом ревью не выполнялся.

**Исправление:** сохранять terminal outcome и завершать сессию при любом неуспехе отправки/подготовки ответа. Проверить частичный header/body, timeout, RST, повторный запрос на том же сокете, обычный успешный JSON и 302.

## Что не следует выдавать за новый дефект или причину

- **Автоматическое captive-окно:** приложение имеет HTTP-302 fallback, но не запускает wildcard DNS и не публикует captive DHCP option. Включённая в sdkconfig библиотека DNSServer не означает работающий DNS-сервис. README:385 предусматривает ручной `http://192.168.4.1`. Поэтому отсутствие автоматического окна — ограничение реализации, не доказанный отказ ручного входа. [Официальный пример Espressif](https://github.com/espressif/esp-idf/tree/master/examples/protocols/http_server/captive_portal) показывает необходимые DNS/HTTP и DHCP-механизмы. Отдельное добавление auto-discovery не является доказанным лечением обрыва HTML.
- HTTP error в журнале означает, что какой-то HTTP-запрос уже достиг Aura. Это исключает чисто DNS-проблему для этого конкретного запроса, но без path/User-Agent не связывает его с нужной попыткой пользователя.
- После обновления ранних beta до 1625a09 исправлены потеря errno за EIO=5, игнорирование finish-ошибки и попытка финализировать оборванный streaming ответ. В старом транспорте SDK chunk failure всегда становился EIO и writer прекращал отправку: утверждение, что 1.2.0 обязательно повторяла частично отправленный chunk, неверно. Terminal protection в новом коде предотвращает такие повторы после появления достоверного EAGAIN.
- Header/status storage живёт до отправки; существующие тесты lifetime/relocation прошли. Возвращение старой проблемы #149 с мусорными заголовками не обнаружено.
- Wi-Fi setup содержит inline HTML/CSS/JS без обязательного внешнего CDN. Отсутствие интернета само по себе не должно мешать ручному входу.
- Scan при старте AP и повторном поиске затрагивает радио; факт ухудшения связи именно у Chris требует hardware capture. Нельзя объявлять это установленной причиной по одному вызову scanNetworks.
- WakePowerGuard может удерживать admission закрытым в fail-closed/display recovery; трёхсекундный флаг в HTTP wait не является жёстким выходом. Это сознательно защищает аппаратный переход. Его нельзя «чинить» без проверки безопасной terminalization владельцем. Связь с двумя жалобами не установлена.
- HTTP server синхронный: ожидание медленного reader задерживает остальные запросы. Существующий send timeout 30 с сохранился; host slow-reader PASS не проверяет радио и всю очередь HTTP task.
- Снимок RAM в новой диагностике показывает internal free/min, но не полный PSRAM largest-block и не пик выделения HTML/JSON. Отсутствие его падения не исключает OOM конкретной аллокации. В текущей конфигурации большие malloc могут идти в PSRAM; тестовые байты ПК не равны бюджету ESP32.

1. **38/38** существующих Unity-тестов: response storage, send capture, stream writer/state/policy, response utils, wifi page, dashboard routing. Runner проверил реальные source identities восьми suite. Evidence: `.pio/native-tests/reports/20261101T150825Z-d2b95a83/00-pio.json`.
2. **5/5 TCP-сценариев** существующего `tools/test_http_stream_sdk.py`: точные complete/slow bodies, RST до body, stalled reader, RST перед finish. Slow reader 2 MiB прошёл за ~8 с; ожидаемые ошибки распознаны. Использованы неизменённые функции выбранного SDK и production capture. Это localhost Windows, не lwIP/ESP32. Первый sandbox запуск не получил доступ к loopback (WSA10013); разрешённый повтор прошёл.
3. Отдельный portal_probe: два дефекта (query root, rescan) и контрольный scan-in-progress case. Handler extraction SHA256 `4637033d246796626d25f7c2b67a1ea8aed7ab6c7cb25fd7b954c7c48f0c1ac1`.
4. robustness_probe: нормальный render и два OOM-триггера на настоящем Arduino String; детерминированная гонка guard плюс последовательный контроль. Только аллокатор и периферийные API подменены. Частота отказов/гонки не измеряется этим стендом.
5. Сопоставлены route/query обработка SDK, chunk send/finalization, session lifecycle, scan wrapper, AP startup, task ownership, MQTT pause, snapshot/queue, memory settings и история диагностики. Новой firmware-сборки нет: код не изменялся, host PASS не квалифицирует BIN.

## Следующий шаг для установления причины, отдельно от исправления findings

Для Chris: точный build/model и полный текст двух записей; точный введённый URL, обычный браузер или captive window; сравнить ручные HTTP `/wifi`, `/`, `/?probe=1` после завершения начального scan. Нужен ответ/статус/число байт в браузере или curl, а не только «белый экран». На уже установленной beta без перезагрузки скачать `/diag` → Download report, чтобы сохранить RAM-историю recent_failures. Serial от старта только в отдельно согласованном сеансе.

Для #158: точный build после обновления, сохраняется ли dashboard, предупреждения с закрытыми вкладками, мониторинг/HA/proxy и свежий diagnostic report. Поле User-Agent/path/peer позволит различить владельца запроса; errno и stage — reset/timeout/finish. MQTT рядом во времени — корреляция, не доказательство общей причины.

Аппаратная матрица после отдельного разрешения: обе модели, чистая AP-настройка и STA, телефон/ПК, прямой HTTP и captive discovery отдельно, scan idle/running/cancel, MQTT off/on/reconnect, контролируемый slow/RST reader, затем следующий обычный запрос и Download report. Снять actual PS mode, scan state, internal/PSRAM largest/free и HTTP stack. Сохранять неисправное состояние до recovery. Ни прошивка, ни factory reset, ни перепубликация в рамках ревью не нужны.

Актуальный порядок после сравнения: сначала повторное закрытие HTTP-сессии (P1), затем сохранение исходного SSID, query/Rescan/OOM/ошибки send/отмена scan; PS guard понижен до P3. Подробные критерии и отдельные вопросы timeout/FailClosed/captive discovery — в [отчёте сравнения](HTTP_AP_REVIEW_COMPARISON_20261101.md). Каждый фикс проверять своим воспроизведением и контролями; ни один не называть «исправлением Chris/#158» до подтверждения соответствующего триггера.
