# Аппаратная проверка AP/HTTP — 2 ноября 2026

**4,3″ оставлена на новом кандидате с исходными настройками. 7″ возвращена на точную исходную Hub-сборку и её данные. Полная аппаратная приёмка не закрыта: на 4,3″ обнаружены два дополнительных сбоя SoftAP, причины которых ещё не изолированы. Публикации нет.**

Это проверка реальных ESP32-S3 по USB и Wi-Fi с Windows, Chrome и Edge. Она дополняет прежние host-проверки, но не заменяет телефоны, физический touch и включение питания. Firmware source и BIN во время этой работы не менялись. Уточнена формулировка предыдущего отчёта: обе инкрементальные команды завершились успешно, без новой компиляции и линковки.

Отрицательные загрузки использовали искусственные данные размером с приложение, без `ota_size`. Это проверка раннего отказа `INVALID_SIZE`, `written=0`, а не полноценной процедуры OTA через экран подтверждения. Отдельно большой POST `/api/settings` вернул HTTP 413 на обоих устройствах. В Chrome/Edge журналы показывают три POST на три попытки каждого браузера, без повторной отправки.

На 4,3″ реальный Rescan в Chrome проверен до автоматического возврата списка сетей — 4,39 с после завершения команды click. На 7″ проверено нажатие и появление Scanning; снимок сделан до следующего опроса. Завершение scan отдельно подтверждено API на обеих платах. Это разные степени проверки, их не следует смешивать.

Плановое пробуждение совмещалось с отрицательной загрузкой: до передачи подсветка OFF, срок расписания внутри передачи, после неё ON; полный HTTP 400 получен на обеих платах (50,33 с и 41,44 с). У 4,3″ последующий retained trace показал завершённый `schedule_wake`, prequiet 110 мс, успешную команду/драйвер. Физический момент появления изображения не измерялся. Время опроса состояния после wake-запроса тоже не является точным временем пробуждения экрана.

В собранных serial-логах нет panic, heap corruption, stack overflow и watchdog reset. Перезапуски были запрошены тестами или USB-инструментом. Финальная диагностика показывает готовые board/LVGL, отсутствие display sync fault и touch read errors. Сообщения об отсутствующих необязательных датчиках, DAC и SD отделены от исследуемых отказов.

## Ограничения передачи и неповторившиеся обрывы

Точные размеры полезных данных: 3 392 656 и 3 394 768 байт плюс multipart-обвязка — около 3,24 МиБ, не 3,39 МиБ.

- На обоих устройствах 40 КиБ/с дали полный HTTP 400 примерно за 82,8 с. При 36 КиБ/с ответ потерян примерно через 91 с; следующий запрос получил 200, перезагрузки не было. Это согласуется с бюджетом дочитывания 90 с, но не означает гарантированной границы для любого клиента.
- На 7″ ограничения 128 и 80 КиБ/с дали ответ за 25,91 и 41,44 с. Пауза отправителя 1,4 с прошла, 1,7 с — нет; после отказа следующий клиент работал.
- В первом прогоне 4,3″ один запрос с ограничением 80 КиБ/с потерял ответ через 36,17 с, отправив 1 888 256 байт. Ещё один запрос завершился до запланированной паузы 1,7 с: отправлено только 700 416 байт при точке паузы 1 МиБ. **Его нельзя считать проверкой паузы 1,7 с.**
- Затем 4,3″ прошла 3/3 на 80 КиБ/с с TCP_NODELAY и ещё 3/3 с обычным Nagle, примерно по 41,4 с. Поэтому считать Nagle установленной причиной нельзя. Первоначальные обрывы не объяснены и сохранены.
- Отдельные паузы 1,4 и 1,7 с при TCP_NODELAY на 4,3″ обе прошли. Размер буферов, место паузы и фактический прогресс на устройстве влияют на исход; предел loopback нельзя переносить на радио как точный порог.
- Ограничение скорости клиента — потолок, а не измеренная скорость радио. Например, первый запрос 4,3″ с потолком 128 КиБ/с занял 63,31 с, фактически намного медленнее установленного потолка.

Параллельное обслуживание во время долгого drain не появилось: HTTP остаётся последовательным. Ограничения 90 с / 8 МиБ / прогресс 32 КиБ за 1500 мс сохранены.

## Два дополнительных наблюдения SoftAP на 4,3″

**1. Потеря Wi-Fi во время Rescan.** В прогоне `ap-repeat` второй поиск сопровождался уходом клиента. Serial зафиксировал уход станции в 01:09:57.884 UTC; Windows — остановку security и disconnect by driver. Таймаут TCP-connect теста наступил в 01:10:00.415, только после него запрошен возврат домашней сети. Следовательно, этот уход начался раньше восстановления сети тестом. При следующем прогоне с ожиданием 8 с вместо 3 с оба scan завершились; это не доказывает, что изменение таймаута устранило причину разрыва. Кроме таймаута изменилось состояние подсветки: первый случай был при OFF, повтор после планового wake — при ON. Это не чистый причинный A/B.

Сохранены serial, Windows WLAN events, время действий и состояние адаптера. Связь scan/радио/драйвера требует отдельного причинного контроля. Документация ESP-IDF различает foreground/background scan, причём выбор делает драйвер; фоновые сканы возвращаются на домашний канал между каналами. Это объясняет, почему радио надо исследовать отдельно, но не устанавливает причину данного события. [ESP-IDF 6.1, scan scenarios](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-guides/wifi-driver/station-scenarios.html#esp32-s3-wi-fi-scan).

**2. Потеря HTTP-подтверждения при сохранении во время scan.** В `ap-repeat2` scan действительно наблюдался активным перед `/save` (01:17:05.321 UTC). Клиент не получил даже строку HTTP-статуса за 6 с. Устройство при этом применило настройки, отключило AP примерно в 01:17:05.899, подключилось к домашней сети и отвечало в STA. Падения прошивки не было. На 7″ аналогичный сценарий вернул полный HTML; раннее обычное сохранение на 4,3″ также было успешным.

Подозреваемая последовательность: [WebWifiHandlers.cpp](../src/web/WebWifiHandlers.cpp) отправляет HTML и планирует STA; [WebHandlersSupport.h](../src/web/WebHandlersSupport.h) задаёт всего 200 мс. Завершение отправки в TCP-буфер само по себе не доказывает доставку по радио до отключения AP. **Это гипотеза по последовательности событий, не доказанный корень.** Те же 200 мс есть в базе `77bfb4b`; регрессию относительно базы без аппаратного A/B заявлять нельзя. Параметры scan 100–300 мс/канал также сохранены от прежних Arduino defaults.

Оба случая должны остаться открытыми при приёмке. Менять только число задержки без причинной проверки и считать проблему решённой оснований нет. Они не доказывают причину Chris или #158: исходные условия и логи тех устройств отсутствуют.

## Чего эта работа не подтверждает

- Реальные телефоны, captive-окно ОС и физическое касание экрана. Полноценного DNS captive discovery в проекте нет; это уже описано в первом ревью. Моя первая попытка теста ошибочно ожидала DNS и была остановлена; после исправления сценария проверялся ручной доступ по IP.
- Полное OTA с физическим подтверждением, неправильной моделью, записью образа и откатом. Проверены USB-запись/восстановление и отрицательные HTTP-upload пути.
- Физическое OFF/ON, отсутствие/наличие батареи и питание. USB/software reset не считается холодным стартом.
- OFF/forget/factory reset во время scan через экран; эти UI-действия не доступны автономно через штатный HTTP API.
- Запас стека scan worker 4 КиБ, длительный soak, send timeout 5 против 30 с. Отсутствие переполнения в этих прогонах не измеряет запас стека.
- FailClosed на реальном устройстве и все редкие гонки. Прежние 150 SDK / 1009 native / TCP5 относятся к host-проверкам; здесь они заново не выдаются за аппаратные тесты.
