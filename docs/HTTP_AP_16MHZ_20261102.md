# Aura AQ: 16 MHz и ограниченное ожидание HTTP

2026-11-02. По согласованному решению владельца 12 MHz исключены из текущего кандидата. Общая прошивка изменена в `firmware-main`, поверх `be397364`; Hub-ветка не интегрировалась и не редактировалась.

## Изменения

- Оба production-профиля используют RGB PCLK **16 MHz**. Адреса GT911 и остальные аппаратные параметры сохранены: 4,3″ `0x14`, 7″ `0x5D`. Удалено утверждение, что снижение PCLK уже доказанно исправляет PSRAM/Wi-Fi bottleneck. Проверенные AP/HTTP, DNS, scan, save receipt и drain исправления остаются.
- Обычные HTTP body до 64 KiB читаются с коротким receive interval 50 ms. При запросе wake HTTP task освобождает activity lease, ждёт разрешения и продолжает тот же SDK request. Socket I/O в защищённых фазах не выполняется, parser-buffered bytes сохраняются.
- Для обычного body действуют независимые пределы: **30 s общего времени** и **1 KiB полезного прогресса за 10 s**. Более короткое тело должно полностью закончиться до progress deadline. Простой byte trickle больше не продлевает запрос. Истёкший запрос получает `408 Request Timeout` и не доходит до прикладного handler.
- Время защищённой display pause исключено из progress budget, но включено в общий. Admission остаётся fail-closed: при зависшем wake owner код не начинает socket operations ради соблюдения внешнего таймера.
- После body read восстанавливается штатный socket receive timeout 10 s. Plain-HTTP receive override сохраняет SDK error contract и не превращает каждую ожидаемую 50 ms паузу в WARN. Заголовки и multipart/OTA по-прежнему используют свои прежние политики. Drain отклонённого запроса остаётся отдельным этапом с прежними bounds; **30 s не являются обещанием полного закрытия соединения**.
- Scan polling отменяет зависший `fetch` через **15 s**, включая чтение JSON body. После ошибки повтор через 8 s; пока scan активен — через 5 s. Следующая попытка начинается только после завершения предыдущей. Некорректный payload тоже приводит к retry, а не молчаливой остановке polling.
- Штатный guard mutation runner копирует новые wiring dependencies и `include`, поэтому baseline control больше не падает из-за отсутствующего файла.

## Основание выбора

16 MHz выбраны как ранее используемый режим с опытом работы у пользователей. Это не заявление о соответствии конкретного модуля общей таблице ST7262 и не универсальная гарантия. В `HTTP_AP_NO_PHONE_20261102.md` сохранены успешные испытания исправленного AP/HTTP на 4,3″ при 16 MHz. Более высокая скорость на 12 MHz не оправдывает дополнительного риска нечитаемого дисплея и усложнения восстановления.

Перед реализацией проверены [ESP-IDF 6.1 HTTP server API](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/protocols/esp_http_server.html), соответствующий локальный SDK `httpd_txrx.c` и [AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController). Повторно использованы существующие подходы проекта: cooperative admission из HTTP close drain и `AbortController` из диагностической страницы. Hub имеет прежний unbounded ordinary-body reader и аналогичный diagnostic fetch helper; перенос изменений туда не выполнялся.

## Проверка

Точные команды, source hashes и результаты: `build/ap-http-16mhz-20261102/`.

- Canonical `scripts/run_native_tests.py`: **1186/1186**, 127 suite/environment entries, 10 invocations; Unity source identity проверена. Манифест и JSON сохранены в evidence/native-reports.
- Полный `tools/test_http_server_sdk.py`: **214/214**, 40 групп, плюс **9/9** handler wiring. Новые S38–S40 отдельно: **26/26**; затем входят в полный прогон.
- `node tools/tests/test_wifi_scan_poll.js`: **8/8**; настоящий встроенный Chromium: **2/2** fault-injection сценария, оба с максимумом одного активного poll.
- `tools/test_http_guard_mutations.py`: чистый контроль **27/27** и **4/4** намеренные регрессии пойманы ожидаемым assertion; build errors/timeouts не засчитывались. Production sources после мутаций неизменны. Первая попытка выявила отсутствующий `test/mocks/Arduino.h` в копии стенда (`guard-mutations/`). Во второй обнаружен неоднозначный anchor четвёртой мутации после добавления нового body reader (`guard-mutations-final/`); anchor уточнён до close-drain участка. Успешный полный повтор — в `guard-mutations-verified/`. Эти две технические ошибки стенда не засчитаны как пойманные мутации.
- Обе предварительные IDF-сборки прошли; после фиксации исходников требуются отдельные финальные сборки с чистой identity (см. candidate manifest).
- `eez_ui_postprocess.py --check`, `git diff --check` и проверка обеих preprocessor-конфигураций прошли: **16 MHz**, GT911 **0x14/0x5D**. Generated UI не менялся.

Новые SDK cases:

- **S38:** два wake во время accepted-body read, отсутствие socket I/O в Switching/Settle/RenderWait, повторное получение lease, побайтово сохранённое тело, ровно один handler вызов и следующий keepalive request с паузой в заголовке больше 50 ms. Wake на Windows host занимал примерно 156 ms; это не гарантия времени на ESP32.
- **S39:** полностью остановившийся sender и byte trickle получают полный 408 примерно за 10 s; handler не вызывается, queued client восстанавливается, lease не остаётся.
- **S40:** регулярные полезные порции проходят progress check, но прекращаются по aggregate deadline примерно через 30 s; partial body не применяется.
- **JS:** восемь состояний настоящей функции из template: зависшие headers/body, network/HTTP error, испорченный JSON, некорректная структура, active scan, completion. Проверяются cancellation, retry, отсутствие перекрытия попыток и очистка timers.
- **Настоящий встроенный браузер:** полная Wi-Fi HTML template с loopback endpoint, который в первой попытке зависает до headers либо посередине JSON. В обоих случаях отмена на 15 s, retry через 8 s, успешный переход `/wifi`; одновременно один запрос. Это браузерный fault injection, не новое испытание радио/captive portal телефона.

## Артефакты и аппаратная приёмка

После локального коммита оба профиля пересобираются штатным `tools/build.ps1` / `scripts/build_idf.ps1`. Финальные BIN, ELF, identity и release artifact stamps сохраняются в `build/ap-http-16mhz-20261102/artifacts/`; точные commit/build ID/SHA-256 — в `candidate-manifest.json`. Старые R7/R8 evidence и артефакты не заменяются. Предварительные сборки до коммита не считаются финальными кандидатами.

Аппаратную приёмку нового BIN нельзя наследовать от R7/R8. На read-only проверке через Mac перед установкой 4,3″ ещё отвечала с `fcb529d-dirty`, 7″ — с исходным Hub `afd6f05-7-dual-i2c-ram-a0`; OTA не была занята, `display_sync_fault=false`, board failure отсутствовал. Эти flags не доказывают нормальное изображение глазами. Изменение PCLK в исходниках само по себе не меняет установленный firmware.

Для короткой аппаратной приёмки: подтвердить конкретную плату и BIN, сохранить актуальные конфиги/состояние восстановления, проверить реальную Wi-Fi страницу, Rescan, save→STA, обрыв/повтор и sleep/wake; попросить владельца подтвердить изображение/касание и физический cold boot. Android проверяется с мобильным интернетом; встроенный браузер не заменяет iOS captive flow. Не откатывать Hub sequence к старому checkpoint ради теста.

Публикации, подписи, push и интеграция Hub не входят в эти локальные изменения. Доступность Mac и старого firmware не считается приёмкой нового кандидата.

## Короткая инструкция пользователю Wi-Fi

При подключении к Aura без интернета выбрать системное предложение остаться в этой сети (название зависит от телефона; Android может предложить `Connect only this time`). Если окно настройки не открылось автоматически, открыть `http://192.168.4.1` обычным браузером, пока телефон подключён к AP Aura. Rescan может занимать около 10–11 s; страница повторяет опрос сама. После сохранения дождаться сообщения о подключении и перехода устройства в домашнюю сеть. Отключать мобильный интернет на телефоне постоянно не требуется.
