## Почему двойное закрытие опасно

`src/web/WebStreamWriter.cpp:111` закрывает клиента при ошибке; после возврата `src/web/WebResponseUtils.cpp:124` закрывает его ещё раз. Для ошибки завершающего chunk первый вызов находится в `WebTransportEspHttpServer.cpp:767`. Метод `stopClient()` (`:690–698`) не идемпотентен: каждый вызов ставит `httpd_sess_trigger_close` в очередь.

В текущем SDK `components/esp_http_server/src/httpd_sess.c:478–483` в очередь передаётся указатель на слот сессии. Первый callback освобождает слот. Между двумя callback сервер может принять ожидающее соединение в этот же слот. При другой активной сессии LRU-счётчик нового слота ненулевой, и проверка в `httpd_sess_close` (`:136–147`) не отсекает второй callback: он закрывает уже нового клиента. Для воспроизведения не нужно ждать 30 секунд или получать OOM.

Повторно собранный production-стенд: клиент K получил 200 и оставил keep-alive; передача клиенту A оборвана; ожидающий N получил `status=0`, WSA 10054. Без K клиент N получил 200. Контроль отличается от production ровно удалением `server.stopClient()` из ResponseUtils: с K и без K клиент N получил полный 200. Временная контрольная копия не переносилась в firmware.

Удаление строки доказало механизм, но ещё не является готовым исправлением: нужно единое владение закрытием / идемпотентный transport и проверка ошибок начала, тела, finish, обычного send, отказа постановки закрытия в очередь и следующего keep-alive запроса. Нельзя потерять закрытие на ветвях, где writer вообще не запускался.

**Почему пропустили:** прежние Unity mocks и TCP-стенд проверяли ошибку передачи, частичный chunk и финализацию изолированно. В TCP-стенде не выполнялись настоящая очередь закрытия сессий и приём следующего соединения между callback. Успешные 38 Unity и 5 TCP сценариев поэтому не проверяли именно этот инвариант. Первоначальный статический просмотр lifecycle оказался недостаточным; это пробел нашего ревью и покрытия, не опровержение нового результата.

## Что перепроверено лично при сравнении

Из прочитанных исходников независимого стенда заново собраны две программы с текущими firmware и SDK-файлами. Использованы настоящий `esp_http_server`, `http_parser`, Arduino `WString` и production web-код, с Winsock/FreeRTOS/Wi-Fi shim. Сервер и клиенты ограничены loopback. Сокеты/тайминг Windows не равны lwIP/радио ESP32.

- S5 production: ожидаемый сброс следующего клиента и успешный контроль без дополнительной сессии — 2 исхода.
- S5 single-stop: следующие запросы успешны в обоих вариантах — 2 исхода.
- S8: испорченный UTF-8 SSID и сохранённый ASCII — 2 исхода.
- S6: пустой HTTP 200; усечённый HTTP 200, 16 367 байт без script/закрывающего HTML; нормальный контроль 24 883 байта — 3 исхода. Оба отказа подготовки остаются вне stream abort history.

Итого при сравнении **9/9 ожидаемых проверок**, из них часть намеренно подтверждает дефект, а не исправность. Это повторное выполнение чужого стенда после проверки кода, не третий независимо разработанный стенд. Все четыре процесса после `unexpected=0` выводят `Failed to send shutdown signal err=-1` при завершении; это ограничение teardown host-стенда, оно сохранено в логах, а не скрыто. Результаты до завершения процесса и TCP-контроли однозначны.

Числа 18 ожидаемых исходов, 5 контрольных и 262 штатных теста относятся к предоставленному независимому отчёту; полный набор 262 при сравнении заново не запускался. Аппаратные результаты не заявляются.

## Коррекции и границы независимого отчёта

1. **WifiPowerSaveGuard:** исправлена наша F2. `NetworkManager.cpp:53` задаёт WIFI_PS_NONE; normal STA-start/connect применяют этот режим. Race в общей переменной остаётся ошибкой синхронизации, но её демонстрация с MIN_MODEM не обосновывает включение power save при нормальном режиме. Не заявляем невозможность при любых будущих настройках/ошибках SDK.
2. **USB errno в 1.2.0:** замечание принято. В установленном пакете libs `5.3.2+sha.cfea4f7c98`, соответствующем Arduino 3.1.1, проверены `CONFIG_LOG_DEFAULT_LEVEL=1`, `CONFIG_LOG_MAXIMUM_LEVEL=1` и отсутствие строки `error in %s` в ESP32-S3 `libesp_http_server.a`. Именно этого WARN из prebuilt HTTP SDK ожидать не следует. Старые `err=5` не восстанавливают истинную причину. USB boot log всё ещё полезен для startup/reset/AP/scan — неверно объявлять его бесполезным вообще.
3. **Вероятность OOM:** запас PSRAM не позволяет без измерений объявить отказ маловероятным: нужны конкретный allocator, доступный largest block и пиковые копии. Сохраняем формулировку «частота неизвестна».
4. **Favicon:** отсутствие отмены в двух host-браузерах опровергает гипотезу только в этих запусках. Нельзя переносить это на телефон Chris, любые версии браузера и реальные сетевые условия. Дополнительный запрос подтверждается сохранёнными логами автора ревью; мы браузерные прогоны не повторяли.
5. **Timeout:** задержка 5,9 с получена с инъекцией блокировки, сокращённой до 6 с. Это проверка реакции синхронного сервера, а не измерение 30-секундного сетевого отказа на ESP32. Сам размер страницы больше TCP send buffer не доказывает зависание: принимающий клиент освобождает окно.
6. **Диагностические эвристики:** пустой HTTP 200 не является уникальным признаком OOM; отсутствие ok_count не означает, что запрос не доходил; большой max_write_ms сам по себе не идентифицирует неисправного клиента. Нужны сопоставленные path, stage, errno, время и ответ.
7. **«Диагностическая beta ничего не исправляет»:** слишком широко. В ней исправлены учёт finish-ошибок и неверная финализация после abort, одновременно добавлена новая регрессия. Корректно: устранение причины исходных жалоб этой beta не доказано.

## Порядок исправлений после сравнения

1. Закрытие сессии: сначала регрессионный тест со следующим соединением, затем исправление владения/идемпотентности и проверки всех стадий; сохранить улучшенную диагностику.
2. SSID: разнести отображаемую подпись и исходные байты выбранной сети. Проверить UTF-8, кавычки/HTML-escaping, ASCII и сохранение введённого вручную имени.
3. AP query, Rescan, контроль полной генерации HTML с явным малым ответом об ошибке, обработка ошибок обычного HTTP send и корректная отмена scan. Для scan проверить позднее завершение и повторный старт.
4. Favicon/HEAD и ограничение времени обслуживания медленного клиента. Таймауты менять по измеряемому бюджету ответа, с контролем медленного рабочего клиента и следующего запроса.
5. PS guard как отдельный меньший приоритет. Политику FailClosed и полноценное captive discovery рассматривать отдельно от ремонта доказанных HTTP-дефектов.

Проверки firmware-изменений должны включать обе IDF-модели и регрессии. Реальная AP/STA матрица, прошивка и публикация — отдельные этапы по правилам проекта. Ни один пункт пока не называть «исправлением Chris» или «исправлением #158» без подтверждения соответствующего триггера.

Доказательства сохранены в `build/http-ap-review-20261101/independent-review/`: исходный текст, исходники/shim и контроль стенда, логи независимого автора, четыре повторных прогона, оригинал нашего первого отчёта, SHA256 манифест. Browser profile и личные данные профиля не копировались. `build.sh` ссылается на локальные main и SDK; точные хеши использованных файлов записаны отдельно в manifest.
