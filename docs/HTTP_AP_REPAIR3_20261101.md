## Исправления

- **Дочитывание HTTP уступает пробуждению.** На границе короткого recv transport освобождает свой activity lease, ждёт разрешения hardware guard и продолжает ту же сессию. Прогресс-таймер исключает вынужденную паузу; отправленный отказ и half-close сохраняются. Предварительное OTA-дочитывание до отправки ответа также прекращает ожидание при запросе wake. Switching/Settle/RenderWait/FailClosed не открываются из HTTP-кода. В штатный синхронный `httpd_config_t.close_fn` добавлено ожидание lease: закрытие после возврата обработчика тоже защищено. SDK остаётся единственным владельцем сессии; повторное async-close не возвращалось.
- **Scan можно остановить до переключения подсветки.** NetworkPlane обслуживает quiescence до попытки нового admission. Остановка относится к уже работающему worker и защищена его существующим lease; mutex сериализует stop, чтение результатов, cleanup и освобождение lease. Worker завершается через штатный blocking SDK scan, без зависимости от Arduino SCAN_DONE. Stop, пришедший раньше фактического запуска драйвера, повторяется. Обычный интервал — 1 с, при wake — 100 мс; одинаковая ошибка не засоряет лог. Ошибка stop не освобождает живую память и не разрешает switch. Прерванный wake scan в AP запускается заново после возобновления network polling.
- **Выключение Wi-Fi, забывание сети, AP/STA ждут завершения scan.** Отложенные команды обрабатываются после release worker; последняя выбранная цель имеет приоритет, а ранее запрошенное удаление SDK credentials сохраняется. Последующий OFF отменяет pending AP/STA; повторное включение после forget сначала выполняет shutdown/erase. Новая политика `WifiScanTransition` покрыта тестами вместе с реальным scan-worker.
- **Медленный отправитель получает больше времени.** Budget teardown увеличен с 30 до 90 с; сохранены 8 МиБ и минимум 32 КиБ прогресса за 1500 мс. Текущий образ на 80/104 КиБ/с получает полный отказ. Это осознанный компромисс с занятостью единственной HTTP-задачи, а не обещание быстрой работы второго HTTP-клиента.
- **Пробелы half-close и send-error закрыты постоянными тестами S21/S22.** Удаление `shutdown(SHUT_WR)` и удаление защиты от drain после ошибки send теперь дают красные проверки. Добавлены S23–S28 для wake, медленной отправки, stop/start race, безопасной смены радио и SDK close.

Не суммировать строки: некоторые детализируют те же SDK-группы. Windows loopback и управляемый Wi-Fi mock не подтверждают радио, телефоны, lwIP и время пробуждения на ESP32. S23 контролирует app send/recv/shutdown/close конкретной сессии в защищённых фазах; фоновые TCP ACK и весь сетевой стек этим тестом не измеряются. `NetworkManager`/`NetworkPlane` целиком на стенде не исполняются: проверены production scan-worker и политика отложенных переходов, подключение к менеджеру проверено чтением кода и обеими сборками.

Браузерный ограничитель считает реальные POST на proxy, ограничивает каждый пересылаемый байт тела и сохраняет RST/FIN. Это отдельная multipart XHR-форма того же типа, а не полный OTA UI/writer/flash. После получения окончательного отказа браузер может прекратить upload; поэтому число пересланных байтов может быть меньше Content-Length. Главное здесь — полный JSON в `onload` и отсутствие повторного POST. Реальный frontend использует `xhr.timeout=0` и отдельные progress/response timers; его код не менялся.

Два промежуточных дефекта стенда сохранены: `sdk-full/s28.log` ошибочно считал переиспользованный Windows SOCKET вторым close старой сессии; итоговый тест считает закрытия до создания следующего клиента. Первый browser proxy требовал переслать весь отклонённый файл даже после onload и помечал корректный HTTP 400 как FAIL. Исправлены условия проверки; окончательные прогоны выполнены заново. Эти неудачные проверки не скрыты и не объявляются firmware-регрессиями.

## Оставшиеся ограничения

**HTTP всё ещё последовательно занят дочитыванием.** 90 с — бюджет одного teardown, а не предел всей загрузки или цепочки browser retries. Остановившийся клиент ограничивается примерно 1,5 с, но продолжающий передавать достаточно быстро может занимать HTTP до 90 с. Пауза guard не продлевает сам wall-clock budget, однако закрытие при истёкшем бюджете ждёт безопасного admission; длительный FailClosed способен отложить его неограниченно. За пределами time/byte/progress лимитов возможны потеря ответа и клиентские повторы. Устранение повторов подтверждено только для указанных браузерных прогонов.

**140/109 мс — измерения конкретных host-сценариев, не общий дедлайн wake.** Другие активные операции, в том числе send с 5-секундным budget, могут задерживать переключение. Ожидания внутри Wi-Fi SDK не получили доказанного жёсткого верхнего предела: успешный stop/возврат driver необходим для освобождения scan lease. Guard при зависшем драйвере намеренно не открывается. Нельзя приписывать штатный finite scan polling всему SDK-вызову; исходная проверка `portMAX_DELAY` остаётся актуальной.

Аппаратная матрица: телефон/ПК в SoftAP, медленное радио/паузы/обрывы и отказ неверного образа; touch тёмного экрана при reject и scan; OFF/forget/AP→STA во время scan; многократные отмены и первый AP boot; worker stack 4 КиБ и heap; сравнение send timeout 5/30 с; длительный прогон обоих профилей. Нужны точные BIN ниже и отдельное разрешение на прошивку. Причина Chris/#158 не установлена.
