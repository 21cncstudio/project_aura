# Перепроверка второй доработки AP/HTTP — 2026-11-01

Последующая [третья доработка](HTTP_AP_REPAIR3_20261101.md) закрывает подтверждённые замечания локально; аппаратная приёмка остаётся открытой. Ниже сохранены результаты сверки предыдущего кандидата.

Основные замечания независимого ревью подтверждены. Точные BIN второй доработки можно рассматривать как кандидаты для отдельно разрешённой аппаратной проверки, **выпуск не принят**. Задержка пробуждения — реальное ухудшение пользовательского поведения, а не только недостающий абзац отчёта. Изменять hardware guard ради уменьшения задержки без проверки нельзя.

В этой сверке production firmware и основной набор тестов не менялись. Сначала сверены все 58 файлов прежнего снимка и 24 артефакта. Новые опыты и мутации выполнены в отдельных ignored-копиях; обновлены только документация и доказательства. Устройства, COM, flash, reset, commit, push и Hub не затрагивались. Связь с Chris и #158 не установлена.

## Почему задержка экрана подтверждена

`esp_route_dispatch` держит WakePowerGuard Activity до возврата `finalizeRequest`, включая весь `prepareSessionClose` (src/web/WebTransportEspHttpServer.cpp:1379, :1298, :718). `WifiScanSession::runScan` держит свой Activity через blocking SDK scan и cleanup (src/core/WifiScanSession.cpp:112).

`WakePowerGuard::evaluateSwitch` не разрешает переключение при active_operations != 0; warning timeout не является разрешением (src/core/WakePowerGuard.cpp:119). `BacklightManager::processGuardedWake` при этом продолжает ждать. Именно это воспроизводят Z5/Z8: они проверяют момент доступности переключения guard, а не физическое включение экрана.

При pending wake NetworkPlane не получает новый Activity и пропускает processAll/poll/обновления connectivity/MQTT (src/core/NetworkPlane.cpp:43). Это пауза логики управления сетью, а не остановка TCP/Wi-Fi драйвера. Guard имеет 2-секундный PreQuiet failsafe с повторным выставлением владельцем, поэтому «почти останавливается» точнее, чем абсолютная остановка. В этот период также может не исполняться scan.poll с его 10-секундной отменой; естественное завершение blocking SDK scan приобретает особое значение.

Из одного журнала первой загрузки 26.10 нельзя вывести гарантию задержки не больше секунды. Это наблюдение конкретного запуска; верхнюю границу нужно проверять отдельно.

## Поправка к утверждению «worker ограничен 12 секундами»

Три объекта, извлечённые заново из фактически используемого `components/esp_wifi/lib/esp32s3/libnet80211.a`, совпали SHA256 с копиями рецензента. В `esp_wifi_scan_start` действительно видны 100-мс опрос и конечное число итераций из `get_total_scan_time(config)`. Для нашего active scan это порядок 10–12 с при обычной работе SDK; [официальный API](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/network/esp_wifi.html) также предусматривает ESP_ERR_WIFI_TIMEOUT. Поэтому обычное ожидание scan не следует описывать как бесконечное ожидание события Arduino.

Но **это не строгая верхняя граница всего SDK-вызова или lease**. До этого цикла выполняется `ieee80211_ioctl`; в нём по пути caller != Wi-Fi task есть `_semphr_take(..., 0xffffffff)` (offset 0x1bc–0x1c9). В esp32s3 adapter это `xSemaphoreTake(..., portMAX_DELAY)`. Также присутствуют mutex waits, а после scan выполняется очистка SDK. Таймер polling-цикла не ограничивает эти ожидания. Это анализ исходников/объектов, не воспроизведённое зависание драйвера и не новый доказанный blocker. Формулировку «lease, значит, тоже ограничен 12 с» принимаю только как оценку штатного пути, не гарантию.

Моя прежняя оговорка про произвольно зависший SDK была защитной границей, но недоговаривала наличие штатного timeout. Теперь оба факта записаны явно. Безопасно считать старый worker завершённым только после его фактического выхода по-прежнему необходимо.

## Уточнения к цифрам и покрытию

- В z_cases `kZImage = 3390144`: это **3,390144 МБ, или 3,2331 МиБ**, а не 3,39 МиБ. Деление на 30 с даёт около **110,36 КиБ/с** до учёта pre-drain, заголовков и буферов. «113 КиБ/с» смешивает единицы; качественный вывод о близкой границе 128 КиБ/с сохраняется.
- 33 уникальные мутации: 29 CAUGHT, 2 NO-RESULT с timeout процесса (yield_every_read и scan_worker_alloc_ignored), 2 SURVIVED. Нельзя называть timeout обычным assertion failure. Недействительный первый прогон не включён в эти числа.
- В исходных mutation JSON half-close проверялся на выбранных s3/s5/s9. Утверждение про весь набор дополнительно проверено мной: без shutdown действительно проходят все 20 групп / 87 assertions.
- Пропуск drain после send error теперь имеет воспроизводящий опыт с причинным контролем. Z7/Z9 подготовлены только в `build/http-ap-recheck2-20261101/work*/`; в основной suite их ещё нет. Это следующий небольшой шаг перед новой доработкой.
- Документ OTA_HARDWARE_TARGET_GUARD.md уточнён: отклонённое тело **может** быть прочитано полностью, но только в пределах cleanup. Префикс по-прежнему проверяется до Update.begin/Update.write. «Файл читается целиком» без этой оговорки тоже неверно.

## Решение и следующий шаг

С выводом «кандидат для контролируемых аппаратных тестов, не для выпуска» согласен. Разрешения на прошивку в этой сверке нет. Зафиксированное UX-ухудшение нельзя считать принятым только потому, что оно не портит flash. До выпуска нужно закрыть задержку wake при HTTP cleanup/scan либо отдельно согласовать измеренную политику; простое удаление lease нарушит смысл hardware guard и готовым решением не является.

Следующая локальная работа: перенести Z7/Z9 в suite; проверить способ своевременно завершать/отменять сетевую работу при pending wake с сохранением подтверждения остановки; отдельно решить границу slow upload/retry. Нужен новый причинный тест, что короткое пробуждение не оплачено доступом к радио во время аппаратного переключения. После этого — разрешённая матрица телефонов/радио/5-vs-30 send budget, Wi-Fi OFF/forget во время scan, stack watermark worker и cold AP start. Не смешивать её с уже пройденными loopback-тестами.
