# Проверка независимого ревью 16 МГц, 2026-11-03

Проверен текущий main `4b52c64b`: firmware-код совпадал с кандидатом `04b770fb`, два последующих коммита меняли только документы. Замечания о совместимости Wi-Fi страницы и слабом S38 подтверждены. Исправления локальные; 16 МГц сохраняются на обоих профилях. Это подготовка следующего кандидата, не разрешение выпуска.

## Что подтвердилось и исправлено

- Весь скрипт Wi-Fi страницы действительно перестал разбираться как ES5 из-за `async`. Отсутствие `AbortController` давало исключение до входа в `try`, без следующей попытки. Polling переведён на асинхронный `XMLHttpRequest`, без Promise/fetch/AbortController. Общий дедлайн headers+body — 15 с; retry при ошибке — 8 с, при активном scan — 5 с, первый запрос — через 2 с. При завершении обработчики отсоединяются до abort; повторные callbacks не создают второй запрос/redirect. Cache-busting timestamp сохранён.
- В той же странице два вызова `NodeList.forEach` тоже мешали выбору сети в старых браузерах. Заменены обычными циклами. Тест выполняет весь скрипт с коллекцией без `forEach`, выбирает две сети и проверяет выбранный SSID/кнопку.
- Прежний S38 пропускает намеренно оставленные 50 мс вместо восстановления 10 с — отрицательный контроль воспроизведён в отдельной копии с исходным `lab_main.cpp` из `04b770fb`. Новый S38 отправляет ведущий CRLF, проверяет фактическое получение двух байт серверным `recv`, выдерживает 3 с и требует полный 200 на том же соединении. Production C++ не менялся. Причину буферизации одиночного `G` этот проход не устанавливает.
- Прежний постоянный mutation runner проверял четыре других guard-сценария. Добавлена группа `--group body`: восстановление таймаута, уступание wake, progress timeout, запрет продления дедлайна одиночными байтами и общий deadline. Default `guard` сохранён; `all` запускает обе группы. Засчитываются только ожидаемые assertion failures, не зависания/ошибки сборки.

Перед правкой проверены существующий polling в Hub-ветке и стандартные API: [MDN XMLHttpRequest](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest), [abort и порядок событий](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/abort), [встроенный timeout](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/timeout). Использован стандартный XHR с одним JS-дедлайном; полифиллы и библиотеки в firmware не добавлялись. Ветка Hub не редактировалась.

## Проверки

Evidence: `build/ap-http16-reviewfix-20261103/`.

- JS: 15 сценариев polling, ES5-разбор всего скрипта через встроенный в Node Acorn и выбор сети без современных API — PASS. Семь целевых JS-мутаций пойманы. Первая подготовка мутаций остановилась из-за неоднозначного текстового якоря до запуска второго мутанта; сохранена отдельно, итоговый набор ограничен Wi-Fi template и прошёл.
- Настоящий встроенный Chromium: зависшие headers и частичный JSON — 2/2. В тестовой странице отключены fetch, AbortController, Promise и NodeList.forEach. Оба запроса реально отменены через 15,000 с, повторены через 8 с, redirect завершён; максимум один активный запрос. Это не эмуляция старого движка/телефона: синтаксис отдельно проверен ES5-парсером.
- Пять C++ body-мутаций пойманы, контроль S38–40 проходит. Старый S38 с тем же дефектом проходит, новый падает на ожидаемом keepalive assertion. Копии, команды, хеши и журналы сохранены; основной C++ transport не изменялся.
- Полный SDK и финальные сборки: результаты будут дополнены после завершения текущего прогона.
- `eez_ui_postprocess.py --check` и `git diff --check` прошли; generated UI не менялся.

Все пять активных виртуальных устройств за 35 с увеличили accepted и sequence на 1, duplicates на 0; errors 1327→1327, started_at по-прежнему `2026-10-25T21:02:56Z`. Предыдущий контроль имел errors=1291: между наблюдениями накопилось 36 ошибок. Их причина этим коротким срезом не установлена; отсутствие ошибок за всю ночь не заявляется.

На момент проверки 4,3″ отвечала с `04b770f`, 7″ — с восстановленным Hub `afd6f05-7-dual-i2c-ram-a0`. Обе `/api/diag` доступны, display_sync_fault=false. Эти данные не подтверждают физическую картинку или работу нового BIN. Службы Mac и платы в этом read-only срезе не перезапускались.

## Границы и приёмка

Подтверждение владельцем физического OFF/ON 4,3″ уже записано в `4b52c64b` и действительно для старого точного кандидата `04b770f`. Исторический остаток в автоматическом отчёте 2 ноября не отменяет дополнение 3 ноября. Новый BIN требует короткого smoke и подтверждения на нём, хотя драйвер/частота экрана не меняются.

Аппаратное уступание accepted-body reader именно физическому касанию остаётся непроверенным: запрос wake через тот же последовательный HTTP server не заменяет касание. Узкий опыт: погасить экран, начать зависший допустимый POST, коснуться экрана внутри 10-секундного окна, сохранить serial/HTTP и подтвердить изображение. Затем получить полный 408 и проверить следующий клиент.

До выпуска нужны телефон на точном новом BIN, экран/касания/физический OFF/ON кандидата 7″ и указанный wake-опыт. Восстановленная Hub-прошивка 7″ не является новым кандидатом. Разница 244–256 и 407–460 КиБ/с из предыдущего прохода реальна; сравнение с прежними 12 МГц не изолирует частоту от условий/других правок. Первопричины редких жалоб Chris/#158 не доказаны. Push/публикация остаются отложены владельцем.
