## Что изменено после замечаний

1. **Ответы при непрочитанном request body.** Сохранён один владелец закрытия: `stopClient()` ставит идемпотентный флаг, обработчик возвращает ошибку, текущую сессию закрывает SDK. Очередь `httpd_sess_trigger_close` не возвращалась. После успешно отправленного ответа transport сначала выполняет `shutdown(SHUT_WR)`, затем ограниченно дочитывает входящие данные, прежде чем вернуть `ESP_FAIL`. Отказы prepare/oversized/multipart и поздний 503 проходят через проверяемый путь отправки. При уже случившейся send-ошибке дополнительное дочитывание пропускается.
2. **Браузерная проверка изменила решение.** Фиксированного дочитывания 1,5 с оказалось недостаточно: сначала Chrome/Edge теряли ответ на 3 МиБ из-за паузы после каждого КиБ, затем Chrome терял его на 128 КиБ/с. Эти неудачные прогоны сохранены. В итоговом варианте пауза выполняется пакетами по 32 КиБ; общий предел дочитывания — 30 с и 8 МиБ, а каждые 1,5 с нужен прогресс минимум 32 КиБ. Остановившийся или капельный отправитель не продлевает этот срок. Все три ограничения независимы от заявленного Content-Length.
3. **Scan без зависимости от Arduino SCAN_DONE.** `WifiScanSession` запускает штатный `esp_wifi_scan_start(..., true)` на отдельной FreeRTOS-задаче. Этот режим SDK не публикует SCAN_DONE; OOM в `Network.postEvent` больше не является условием завершения нашего scan. NetworkManager остаётся владельцем start/cancel/poll, worker владеет результатами SDK и публикует completion только после cleanup и освобождения WakePowerGuard lease. Хранятся максимум 15 лучших уникальных SSID. По 10-секундному deadline запрашивается stop, повторные попытки не чаще раза в секунду. До подтверждённого возврата старого worker его память не освобождается, новый scan/STA не начинает использовать результаты старого.
4. **FailClosed возвращён к прежней политике.** Превышение 3 с меняет будущий ответ на 503, но обработчик продолжает ждать admission. Он не открывает guard и не инициирует HTTP-ответ/закрытие сокета внутри запрещённого окна. После разрешения владельцем отправляется 503; ветка снова достижима и проверена. Вечный FailClosed намеренно остаётся закрытым до действия владельца — автоматического восстановления hardware guard нет.
5. **Уточнение `free(this)`.** No-op deleter заимствованного `global_user_ctx` оставлен. Это латентная ошибка времени жизни; штатного production-вызова stop нет. Она не объявляется причиной пользовательских жалоб.

Остальные исправления первого прохода сохранены: UTF-8 SSID, AP query/Rescan, контроль полноты HTML при OOM, учёт send-ошибок, favicon/HEAD, синхронизация PS guard и его baseline. Dependencies и генерируемый UI не менялись.

### Существенные пределы и компромиссы

Дочитывание синхронное: **отклонённая, но достаточно быстро продолжающаяся загрузка может занять HTTP-задачу до 30 с** и удерживать activity lease. Это не обещание обслуживания других HTTP-клиентов за 5 с в таком сценарии. Остановившийся/капельный клиент ограничивается примерно 1,5 с, но полезный поток получает время закончить отправку. Сервер не хранит всё тело в памяти. Клиент за пределами time/byte/progress бюджета может получить сетевую ошибку вместо JSON; неограниченной гарантии доставки нет. Отдельное прежнее OTA pre-drain — до 32 КиБ/1500 мс перед ответом.

5-секундный send budget относится к одной операции chunk/plain response, **не ко всей странице, загрузке или завершению соединения**. Параметры send/close нужно проверить на радио; сравнение send 5/30 с остаётся в аппаратной матрице. FailClosed может ждать неограниченно по исходной hardware-политике.

Scan больше не ждёт потерянный Arduino callback, но это не доказательство восстановления из навсегда зависшего внутреннего SDK API. Если драйвер не возвращается даже после stop, старый worker сохраняется, чтобы не освободить его живую память; принудительное убийство задачи/сброс платы не добавлены. На устройстве ещё нужны измерения 4-КиБ стека worker, heap, AP→STA, отмены и wake. NetworkManager целиком на host-стенде не исполняется.

## Основание выбора решения и следующий этап

Изучены [RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6), исходники локальных SDK HTTP/lwIP, [Chromium HttpStreamParser](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/http/http_stream_parser.cc), [официальная модель scan ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-guides/wifi-driver/overview.html#wifi-event-scan-done) и [API Wi-Fi](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/network/esp_wifi.html). Hub использует прежний путь и готового применимого исправления не дал. SDK-дочитывание без наших пределов может затянуть единственную HTTP-задачу; переход обратно на async-close вернул бы опасное владение сессией. Выбран штатный TCP half-close с ограниченным drain. Для scan выбран штатный blocking API на worker вместо собственного счётчика теряемых Arduino-событий.

Следующий этап — независимая проверка этого дерева, особенно компромисса 30-секундного HTTP drain и границ scan cancellation, затем отдельно разрешённая аппаратная матрица. [Запрос для повторного ревью](HTTP_AP_REPAIR2_REVIEW_REQUEST_20261101.txt). Ничего не опубликовано и не прошито.
