# Сверка независимого ревью AP/HTTP, 2026-11-02

Ревью проверено против main `1a88628d` / production `ec484f81`. Найдена действительная регрессия диапазона scan; риск потери `/save` подтверждается кодом, но причина конкретного Android-сбоя не изолирована. Пробел lease-теста воспроизведён в отдельной копии. Выпуск по-прежнему не готов.

Production source, постоянные тесты, BIN, устройства/COM, настройки Wi-Fi и Hub в этой сверке не менялись. Новых аппаратных прогонов и firmware-сборок не было. Изменяется только документация. Новые эксперименты из вложенного отчёта рассматриваются как предложения, не как команды пользователя.

## Подтверждено

1. `src/core/WifiScanSession.cpp:148–157` ограничивает grouped scan `schan..schan+nchan-1`, не учитывая различие AUTO/MANUAL. Локальный SDK 6.1 `esp_wifi.h` документирует начальный `01/1/11/AUTO`; наш src не меняет country. Поэтому при этом состоянии каналы 12–13 никогда не запрашиваются. [Espressif FAQ](https://docs.espressif.com/projects/esp-faq/en/latest/software-framework/wifi.html) описывает их пассивное сканирование по умолчанию, а [ESP32-S3 Country Code](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-guides/wifi-driver/overview.html#wi-fi-country-code) различает AUTO с пассивными дополнительными каналами и MANUAL. Это регрессия относительно прежнего all-channel scan. Фактическое обнаружение роутера на канале 13 ещё не проверялось. Исправление должно сохранить country policy и active/passive semantics; просто поставить максимум 13 для всех стран/политик недостаточно. A37 использует вымышленный диапазон 3–8 и проверяет его соблюдение; теста world-safe AUTO нет.

2. `src/web/WebWifiHandlers.cpp:82–83` игнорирует bool `sendHtmlStream` и всегда планирует переход STA. Даже true означает завершение передачи в локальный socket API, а не подтверждение получения HTML браузером. В `4_3/radio-sta-native/diag-before.json` действительно `/save`, 4144/4144, max_write=4 мс, abort=none. Эти счётчики совместимы с потерей доставки при снятии AP. Исправление grace после scan устраняло конкретную гонку, но не доказывало завершение доставки. Обработка false нужна отдельно; её добавление само по себе не объяснит случай с true.

3. A38 не проверял удержание activity lease в паузе между каналами. Четыре своих запуска в отдельной копии: текущий A38 PASS; release-before-home с текущим A38 PASS; усиленный A38 на правильном коде PASS; усиленный A38 на мутации FAIL ровно по `worker retains activity lease throughout home dwell`. Дополнительная проверка сделана пока только в диагностической копии. В рабочем коде lease удерживается правильно. Нужны также барьеры для следующего SDK start и финального освобождения: независимые журналы показывают выживание удаления последнего mutex. SDK-мутация lease проверялась автором на S30/S31, это не весь SDK-набор.

4. Анализ сохранённых pcap воспроизводит повышенные RTT/ACK на 4,3″. Независимый скрипт даёт idle median 13,8/2,2 мс в AP и 16,7/2,8 в STA. Его idle означает «вне больших upload-потоков», включая промежуточные HTTP. Наш отдельный расчёт строго первых 9,5 с до нагрузки: AP 9,65/2,03 мс (42/46 ответов), STA 16,71/2,89 мс (45/46). Вывод о разнице сохраняется, абсолютные числа зависят от окна. ACK/zero-window измеряют TCP на Mac, не время выполнения функции Aura. Поле `unique_kib` независимого tcp_stats.py фактически включает повторы; как объём уникальных байт его не используем.

5. Runtime действительно различается: диагностические снимки показывают 3 framebuffer без native renderer на 4,3″ и 2 с native renderer на 7″; I2C у 4,3″ общий. Поэтому одинаковый sdkconfig не исключает разницу CPU/памяти/планирования. Фраза «это не HTTP-код» слишком категорична: ping доказывает задержку вне HTTP-обработчика, но не исключает влияние общей прошивки на планирование/ресурсы и отдельные дефекты HTTP. Причина «железо» пока не доказана.

## Хронология и ограничения выводов

- В serial есть SDK send errno=116/status=200 в 13:36:54 UTC и `reason=send_failed`. Этот путь простого send не обновляет потоковые HTML-счётчики; их отсутствие не опровергает сетевую ошибку. Диагностику простых ответов следует улучшить.
- В моём предыдущем отчёте «не уложился в 100 с» было неточным: 100 с — опция max-time, фактические exit/stderr не сохранены. Файл с traceback уже закончен в 13:36:58.510 UTC; заполненная форма записана в 13:38:15.716, затем нажата кнопка. Предыдущий тестовый процесс был завершён до POST, поэтому гипотеза «curl ещё висел» не поддерживается хронологией. Исправность канала перед самим POST, однако, не проверена; нужен отдельный чистый опыт. Корень конкретного отказа по этим материалам не установлен.
- `radio-matrix-4-traced`: scan не наблюдался status polling — это верно, но НЕ означает, что он не запускался. Полная страница шла 5,86 с, первый status через 6,20 с; завершение scan до первого опроса правдоподобно. Размер HTML не является уникальным доказательством успешного окончания scan. Подтверждённый отказ — последующий 12-секундный таймаут запроса.
- Mac 15/15 не заменяет повтор исходного AX211-сценария. Windows Wi-Fi после запроса пользователя не переключался; исходный Windows event сам по себе не доказывал firmware-разрыв. Android 4,3 OFF/wake и полная AP-матрица остаются незавершёнными. 5/10 неудач полных отказных upload 4,3 относятся к разным условиям; это не оценка вероятности отказа одного одинакового сценария.

## Предложения из ревью требуют проверки

Half-close и ожидание клиентского FIN — разумный кандидат для более аккуратного завершения соединения, но FIN сам по себе не подтверждает чтение ответа: направления TCP закрываются независимо, клиент вправе закончить отправку запроса до получения ответа. Нужен тест такого клиента, ограниченный fallback и проверка TCP-доставки либо прикладного подтверждения. Это следует из [RFC 9293, half-closed connections](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6.1). Возвращаться к фиксированному увеличению задержки без критерия доставки не стоит.

[AOSP NetworkMonitor](https://android.googlesource.com/platform/packages/modules/NetworkStack/+/refs/heads/main/src/com/android/server/connectivity/NetworkMonitor.java) действительно проверяет link-local/site-local/ULA. [CDFER example](https://github.com/CDFER/Captive-Portal-ESP32/blob/main/src/main.cpp) использует 4.3.2.1 и объясняет выбор Samsung. Это правдоподобный диагностический обход конкретного условия, не доказанная совместимость Aura и не готовое решение для выпуска. Публичный адрес может конфликтовать с маршрутами клиента; смена AP IP затрагивает UI/URL/DNS/DHCP/redirect. В этом ревью ни адрес, ни конфигурация Android не менялись. Утверждение, что альтернативой может быть только HTTPS CAPPORT, было бы слишком узким; такого вывода делать не следует.

Минимальный Wi-Fi-only образ полезен для A/B, но результат 14 мс не докажет железо: драйвер, PHY/NVS, энергосбережение и радиоусловия останутся переменными. Сравнивать нужно одинаковый SDK/радиопараметры, поэтапно включая runtime, сохраняя backup и возврат. Перестановка плат отделит место от экземпляра, а не железо от прошивки. Точные 2/14 мс не являются критериями приёмки.

Порядок следующей доработки: восстановить корректный поиск каналов и закрыть lease/mutex регрессии; отдельно исправить завершение `/save` и добавить диагностику простых ответов; затем чистая телефонная матрица и контролируемый Wi-Fi/runtime A/B. До этого выпуск остаётся заблокирован.

Материалы: ignored `build/ap-r6-check-20261102/`. Сохранены оригинальный текст, скрипты и журналы независимой проверки; свои 4 A38-прогона, проверенный целевой FAIL, pcap-пересчёты и timeline. Полные 1022/162/224/65 наборы в этой сверке повторно не запускались. Wrapper после целевого FAIL сначала не учёл два пробела в выводе; сравнение нормализовано и проверено без повторного прогона. Firmware/BIN неизменны.
