## Подтверждено лично

Из текущих production-файлов заново собран SDK-стенд с предоставленными `x_cases.inc` и регистрацией дополнительных маршрутов. Эти маршруты повторяют response path отказа OTA и вызывают настоящий transport; полноценный OTA writer на устройстве не запускался. Использованы текущий SDK, Arduino String, loopback/Winsock. Процессы завершились штатно.

| Проверка | Текущий код | Контроль: разрешено SDK-дочитывание |
| --- | ---: | ---: |
| Отказ multipart upload, 1 МиБ | ответ 400 доставлен 0/12 | 12/12 |
| Обычный POST, 256 КиБ при лимите 64 КиБ | ответ 413 доставлен 0/12 | 12/12 |

Механизм подтверждён исходниками: `httpd_sess_process()` возвращает ошибку сразу после неуспешного `httpd_req_new()`; `httpd_req_delete()` с циклом дочитывания не вызывается. Новый `ESP_FAIL` попадает именно на эту ветку. `send_upload_json_response()` заранее дочитывает только до 32 КиБ/1500 мс. При оставшихся входных данных немедленное закрытие способно сбросить соединение и потерять ответ. В текущем lwIP `tcp_close_shutdown()` при непрочитанных данных вызывает RST и purge.

Контроль меняет только возврат результата transport/prepare failure на ESP_OK; он не реализует требуемое закрытие и **не является готовым исправлением**. К двойной очереди `httpd_sess_trigger_close` возвращаться нельзя. Нужен один владелец закрытия и корректное завершение TCP после ответа, с ограниченным чтением и временем. Та же проблема закрытия и способ поэтапного завершения описаны в [RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6).

Для будущей регрессии проверять доставку полного status/body, следующий клиент, отказ до/в начале/в конце загрузки, oversized POST, прерывание отправителя и остановившегося отправителя. Не превращать исправление в неограниченное дочитывание всего заявленного Content-Length.

## Остальные замечания

1. **Потеря SCAN_DONE — реальный пробел восстановления.** `NetworkEvents::postEvent()` может вернуть false при отказе new; `WiFiGeneric` его не обрабатывает. `WifiScanSession` ждёт счётчик callback, `startSta()` откладывается, а deadline безопасного выхода отсутствует. Это подтверждено по коду, не на радио. Простого сброса active по таймеру недостаточно: запоздавшее событие может завершить уже следующий scan. Нужен ограниченный recovery с подтверждённым завершением старой операции и защитой от её позднего callback; тестировать и потерю, и задержку события.
2. **5 секунд — пока экспериментальный параметр.** Loopback доказывает ограниченность операции и прохождение проверенного медленного клиента. Он не определяет допустимый порог для слабого радио/телефона. Сравнение 5/30 с требуется в аппаратной матрице после устранения блокеров. Расчёт числа TCP retransmissions сам по себе не является измерением на плате.
3. **`free(this)` — латентный дефект, не объяснение жалоб.** В текущем production есть создание/начальный begin, вызова stop нет; остаётся деструктор. Исправление заимствованного global context оставить, прежнюю формулировку о возможном stop в пользовательском сценарии снимаем. Независимое ревью дополнительно проверило отсутствие вызова в v1.2.0; прежняя сверка уже установила наличие неверного deleter там.
4. **FailClosed: замечание о границе задачи принимается.** Предыдущее сравнение оставляло политику отдельным вопросом. Наш guard формально не открывается, однако принудительное закрытие сокета без admission не доказывает сохранение прежнего запрета сетевой активности. Нужен отдельный разбор/возврат поведения; отсутствие HTTP body не равно отсутствию FIN/RST. Ветки 503 в текущем коде действительно недостижимы: при превышенном времени функция возвращает пустой Activity и раньше срабатывает ESP_FAIL.

Независимые 1009 native, 70 SDK assertions, 5 TCP, проверки 24 артефактов/55 файлов и mutation testing не переобъявляются новым личным полным прогоном. Прочитаны их материалы, лично повторены два новых случая и причинный контроль. Браузерные Chrome/Edge и curl запуски в этой сверке не повторялись. Поведение ESP32 по RST следует из исходников, не из измерения на устройстве.

## Вывод и материалы

Двойное закрытие было исправлено, но новая стратегия завершения добавила регрессию доставки отказов. Это ошибка реализации и пробел моего покрытия: тесты проверяли, что ошибка закрывает соединение и не убивает следующий запрос, но не проверяли сохранность ответа при продолжающейся отправке request body. Прежний вывод о завершённости локальной доработки снимается.

Следующая последовательность: корректное завершение отказов с unread body и регрессии → bounded scan recovery с late-event защитой → отдельное решение по FailClosed → полный прогон и обе сборки → разрешённая аппаратная матрица, включая send budget. Это план доработки, не заявление о её выполнении.
