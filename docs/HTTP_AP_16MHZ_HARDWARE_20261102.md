# Aura AQ: аппаратная проверка кандидата 16 МГц

2026-11-02. Проверен точный чистый кодовый коммит **04b770fbc5bf18f3f3e9d73c1583ec50f8b047b2** на обеих платах. Сетевые проверки шли через MacBook `aura-ha-lab`, Ubuntu/b43; браузер — установленный Chromium через Playwright CLI. Windows использовалась для USB, хранения артефактов и управления Mac, не как Wi-Fi-клиент тестируемого AP.

**Результат: автоматический сетевой/контроллерный smoke пройден на обеих платах.** 4,3″ оставлена на новом кандидате, 7″ возвращена на исходный Hub. Изображение, физические касания и полное снятие питания владелец пока не проверял. Причина исходных единичных жалоб пользователей не установлена.

Владелец явно разрешил прошивку и тесты, затем уточнил порядок: «собирать прошивать и тестить», «запушим когда решим все проблемы». Для этой работы согласовано исключение из прежнего правила «сначала GitHub». Push и публичный выпуск не выполнялись; remote main при финальной проверке осталась на `77bfb4b0`. Hub-исходники не менялись и не интегрировались.

Остановившийся sender и byte trickle получили полный 408 через 10,01–10,08 с. Передача с достаточным полезным прогрессом остановлена общим пределом через 30,04–30,06 с. Частичное тело содержало корректное начало команды выключения подсветки, но настройки не применились. Следующий клиент восстановился за 0,03–1,15 с; обрыв body также не оставил сервер недоступным. Это реальные сокеты ESP32. Уступание body-reader защитным фазам пробуждения проверено SDK-стендом; аппаратный wake в этом проходе выполнялся через API во время scan, без физического касания во время body read.

Принятые UI Rescan: 4,3″ **9,21 / 9,91 с**, 7″ **9,22 / 9,49 с**. Браузер использовал собственный polling/redirect страницы. После заполнения формы видна страница **Starting connection**, затем API подтвердил STA по исходному адресу. Скриншоты сохранены в evidence. Телефон, автоматическое captive-окно Android/iOS и ручной no-JS сценарий на этих точных BIN в этом проходе не проверялись.

Полные передачи: 4,3″ **243,8 / 255,7 КиБ/с**, 7″ **407,1 / 460,1 КиБ/с**. Одинаковый TCP-клиент, TCP_NODELAY, включённая подсветка, каждый раз отправлены все 3,4 МБ. Это не одновременный A/B с 12 МГц и не доказательство причины прошлых низких скоростей. На обеих платах наблюдалось примерно **39 Гц** по refresh callbacks; display_sync_fault=false, framebuffer wait timeout/ownership violation/touch read error — 0, touch_offline=false. Контроллерные flags не заменяют просмотр картинки и проверку касаний.

## Запись, восстановление и границы

Перед записью каждая плата повторно опознана по native USB serial/MAC и живым profile/hostname: 4,3″ COM5 `94:A9:90:04:6F:48`, 7″ COM10 `20:6E:F1:AB:14:70`. Другие COM не открывались. Полные свежие копии по 16 МиБ сохранены. Первичная запись изменяла только приложение в текущем OTA slot, с полным readback и доказанным равенством вне записанного диапазона. AP включался временным изменением только двух config-файлов; содержимое остальных файлов LittleFS проверялось.

- **4,3″:** оба исходных `config.json` / `config.last_good.json` восстановлены побайтно с readback, другие файлы в этой операции сохранены. Итог — `04b770f`, 16 МГц, исходный STA `.54`, последние 8 HTTP-проверок PASS. В заключительном снимке uptime 1197 с после финального upload reset, без нового запуска за это окно.
- **7″:** возвращён весь свежий исходный flash/LittleFS, полный readback совпал с backup. Восстановлена `afd6f05-7-dual-i2c-ram-a0`, STA `.91`, итоговые 6 проверок исходного Hub PASS. Файлы вернулись к состоянию начала снимка; тестовые изменения примерно за 18 минут отменены. Это не сохранение истории, набранной в тестовом main.
- В отличие от прежнего опыта, исходный Hub **не запускался между снимком и тестовой прошивкой**. Backup сохранил reserved sequence **126336**. После восстановления наблюдались HTTP 200, sequence **126338 → 126340**, uploads **2 → 4**, failure_count=0 в новом runtime. Кода 409 в этом окне нет. До теста счётчики исходного runtime уже содержали 3 ошибки при последнем HTTP 200; эти старые ошибки не выданы за новые и не скрыты.
- Mac вернулся в Meotida/network 0; созданные AP network entries удалены, четыре исходных службы active. Два временных файла передачи Wi-Fi реквизитов удалены. Оба браузерных сеанса закрыты. Пять активных виртуальных отправителей из текущего status.json за заключительные 35 с каждый получили новое accepted/sequence, без новых duplicates/errors; служба не перезапускалась (started_at 2026-10-25). Все **6** собственных serial-логгеров STOPPED, TX=0, fatal=[]; auto-reconnect не оставлен.
- Выполнялись USB upload resets; **физических OFF/ON не было**. Успешный положительный OTA с физическим подтверждением также не проверялся. Нагрузка и короткий smoke не являются длительной квалификацией всех экземпляров панелей.

## Сбои самого стенда

Первая попытка 4,3″ прочитала полный backup, затем остановилась из-за отсутствующего LittleFS-модуля в выбранном Python. Приложение ещё не записывалось. Работа продолжена существующим LittleFS-окружением сборщика из того же снимка, пока плата оставалась в loader.

Первый браузерный проход 4,3″ успешно выполнил один Rescan, но парсер стенда не принял новый Playwright ref `f2e23` вместо `e23`. Ссылка была в snapshot. Первая попытка сохранена в `remote/4_3/browser-save/`; принятый полный повтор — `browser-save-verified/`. Production-код из-за этого не менялся. Один management SSH status-запрос во время возврата Mac с AP 7″ получил timeout; следующий подтвердил успешно завершённый сценарий и восстановленную сеть. Эти события не засчитаны как firmware PASS или как дефекты firmware.

## Доказательства и следующий шаг

Все материалы — **`build/ap-http16-hardware-20261102/`**: `SUMMARY.json`, `preflight.json`, `live-before.json`, `live-after.json`, `authorization.json`, `local-only-decision.json`, `preservation.json`, свежие backup/readback, serial, принятые и исключённые результаты Mac, снимки браузера и проверенные helper scripts. `remote-evidence-manifest.json` фиксирует 190 файлов и архив по SHA-256. Приватные конфигурации и pcap остаются только в ignored evidence. 305 старых BIN/evidence-файлов и исходное состояние dirty Hub/архива сохранены.

Решение остаётся прежним: **16 МГц для обоих профилей, без перехода на 12 МГц**. Следующая приёмка — глазами проверить экран и касания, выполнить настоящее снятие питания на точном кандидате, затем повторить настройку с телефона. Для ручной проверки именно нового кандидата 7″ потребуется снова установить его BIN: восстановленная Hub-прошивка не является его проверкой. До решения владельца о завершении проблем push/публикация не выполняются. Настройка телефона без интернета должна объяснять выбор «остаться в этой сети» и резервный адрес `http://192.168.4.1`.
