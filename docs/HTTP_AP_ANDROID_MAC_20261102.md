# AP/HTTP: Android, Mac и радио, 2026-11-02

Статус: этот аппаратный прогон завершён, устройства и стенды восстановлены. Общая приёмка AP/HTTP НЕ закрыта: Android/SoftAP на 4,3″ остаётся нестабилен, подтверждение `/save` один раз потеряно. Локальные исправления и тесты сохранены отдельно от решения о выпуске. Выпуск не разрешён; связь с жалобами Chris и #158 не доказана.

## Границы и среда

Пользователь разрешил прошивку обеих плат, автономные тесты и локальные коммиты. 4,3″ можно оставить на новой прошивке, 7″ необходимо вернуть на Hub. После указания «через мак» сетевые прогоны идут на MacBook, а не на Windows Wi-Fi. Компиляция и host-тесты остаются на Windows. Телефон подключён по USB/ADB.

Физические касания экрана Aura и iOS не автоматизированы. Пробуждение в матрице вызывается через API с проверкой фактического состояния и наблюдаемого пересечения со scan.

Все первичные материалы — ignored `build/http-ap-acceptance-20261102/`. Полные flash-backup и конфигурации содержат частные настройки; они не входят в Git. Серийные журналы имеют UTC, TX=0. Reset через esptool не называется физическим холодным включением.

## Подтверждённые дефекты и изменения

1. AP выдавал клиентам DNS 192.168.4.1, но сервер DNS отсутствовал. Android с включёнными мобильными данными оставлял обычный Chrome на мобильном маршруте: ручной IP давал 502, тогда как запрос, привязанный к wlan0, получал полный HTTP 200. При отключении мобильных данных Chrome открывал страницу. После добавления AP-only DNS в раннем опыте Android распознал CAPTIVE_PORTAL и открыл полную страницу Aura в штатном captive portal при mobile_data=1; свежие подключения позднее показали ограничение Android private-IP detection, описанное ниже. Первый автоматический popup не был зафиксирован: использована системная строка «Sign in to the network». Обычный Chrome по ручному IP всё ещё может выбрать мобильную сеть; это не равнозначно работе системного captive portal.
2. All-channel scan надолго уводил единственное радио с AP-канала. Новый worker проходит разрешённые country-каналы по одному, с прежним dwell 100–300 мс и не менее 120 мс дома между каналами. Сохраняются lease, stop/cleanup mutex, отмена, дедлайн, дедупликация и ограничение 15 результатов. STA-only сохраняет один SDK scan channel=0. Ошибки country/cleanup останавливают операцию.
3. Окно progress 32 КиБ/1500 мс теряло ответ даже при быстрой передаче с TCP-повторами. На 7″ сохранены повторные передачи одного sequence и последующий RST; serial дал progress_timeout при 29664 байтах за 1519 мс. Окно увеличено до 5000 мс. Общие 90 с/8 МиБ и уступка wake не менялись. Остановившийся отправитель теперь может занимать HTTP примерно 5 с; это сознательная цена устойчивости к потерям. Предварительный drain перед ответом остаётся 32 КиБ/1500 мс. HTTP остаётся последовательным; повтор браузером означает новую попытку с новым бюджетом.

DNS: без отдельной задачи, без аллокаций на пакет, nonblocking, bind только AP IP:53, максимум два пакета за poll под существующим network admission. Ошибка сокета закрывает его один раз, NetworkManager повторяет старт через 5 с. Пакет ограничен 512 байтами; oversized определяется 513-байтовым receive buffer. Один uncompressed IN question, A/ANY возвращает AP IPv4 с TTL=0, другие типы — NOERROR без ответов. Дополнительные/EDNS записи не отражаются. В AP-redirect добавлено тело, а HEAD сохраняет Content-Length без передачи тела.

## Проверенные готовые решения

- [Espressif captive portal example, v6.1](https://github.com/espressif/esp-idf/tree/v6.1/examples/protocols/http_server/captive_portal): использована модель DNS+redirect и рекомендация непустого redirect body. Пример с отдельной blocking-задачей не согласуется с Aura WakePowerGuard; штатный Arduino DNSServer использует отдельный AsyncUDP callback и неподходящий для наших требований разбор QName. Поэтому применён небольшой ограниченный owner-polled сервер, с отдельными тестами I/O и пакетов. Аппаратная совместимость с iOS этим не доказана.
- [Espressif grouped SoftAP scan](https://docs.espressif.com/projects/esp-idf/en/v5.4-beta1/esp32/api-reference/provisioning/wifi_provisioning.html), точная локальная реализация `managed_components/espressif__network_provisioning/src/manager.c`: группировка и 120 мс дома. Полный provisioning manager владеет собственными глобальными транспортами/событиями и не заменяет текущий worker без изменения архитектуры. Перенесён подход, не весь manager.
- Реализации Hub проверены: прежний Arduino scanNetworks(true), готовой группировки и нужного DNS owner lifecycle там нет. Hub source не изменялся и main туда не интегрирован.

## Базовые наблюдения и неудачные попытки

- Windows `pc-rescan-1` прерван сменой сети по запросу пользователя. Event 8003 совпал с указанием перейти на Mac. Этот образец исключён из чистых доказательств разрыва прошивкой; прежняя промежуточная формулировка исправлена.
- Mac 4″ до группировки: 9/9 scan-сценариев прошли. Mac 7″: одна серия оборвалась таймаутом HTTP 9 с после запроса wake, Wi-Fi association сохранилась, следующая диагностика ответила; повторная серия 9/9 прошла. В повторной серии ping за весь прогон: 266 отправлено, 164 получено. По pcap до сценариев 49/47 (~4% потерь), во время сценариев 213/113 (~47%); небольшая разница общих счётчиков связана с окном захвата. WPA фиксировал beacon loss. Это корреляция, не доказательство причины каждого таймаута; b43 исторически терял пакеты и в домашней сети.
- Старое progress-окно: Mac 7″ ON получил полный 413 в 2/3 загрузок (473 и 541 КиБ/с), одна оборвалась. 4″ ON без телефона: 1/3 полных ответов, 105–118 КиБ/с фактически переданных данных. В отдельной серии с подключённым телефоном 4″: 0/3. Межпрофильное сравнение серии с разным числом клиентов не используется как чистый контроль.
- Старый phone API matrix остановился ещё до сценариев: /api/diag отдал 5665/6349 байт и достиг 12 с. Последующий контроль дал полный 200 и 5/5 ping. Нельзя записывать эту попытку как 15 выполненных сценариев.
- Неудачное присоединение Mac к 4″ до направленного probe и конфликт имени watchdog для 7″ — ошибки настройки стенда, сохранены отдельно. Текущий helper использует одинаковые fixed BSSID/2412 MHz probes на обоих профилях.
- Alarm wake мешал OFF-precondition: активная тревога включала экран. Для контролируемых тестов временно отключены alarm wake и schedule; исходные конфиги сохранены для восстановления.

## Аппаратные результаты Mac

На финальном BIN 4,3″: 15/15 Rescan (5 ON, 5 OFF, 5 wake), во всех наблюдался активный scan; соединение и полные страницы сохранены. На 7″ первая серия дала 10 успешных обычных scan и один непокрытый wake: стенд принял первый false асинхронного snapshot за завершение до наблюдения старта. Это не засчитано как wake PASS или обрыв радио. В стенде исправлено ожидание actual start, повтор дал 15/15. Код устройства для повтора не менялся. Штатная страница начинает status polling через 2 с, а ранний тест опрашивал почти немедленно.

На новом 7″ полный файл 3 393 552 байта и HTTP 413: ON 3/3, 427–462 КиБ/с; OFF 3/3, 432–465 КиБ/с. Ограничение 40 КиБ/с: 1/1, 82,85 с. На 4,3″ при том же Mac и одном клиенте: ON 2/3 (39–51 КиБ/с полные, третий исчерпал 90 с); OFF 1/3 (45,7 КиБ/с полный, ещё два исчерпали 90 с). При потолке 40 КиБ/с фактические 35,1 КиБ/с также исчерпали 90 с. Эти неудачи не скрыты и не названы PASS.

Короткий контроль на 512 КиБ, три повтора каждого варианта:

| TCP-клиент Mac | 4,3″, КиБ/с | 7″, КиБ/с |
| --- | --- | --- |
| Nagle, SO_SNDBUF=8192 (Linux фактически 16384) | 30,7–50,0 | 420–463 |
| TCP_NODELAY, тот же буфер | 37,2–42,0 | 407–539 |
| TCP_NODELAY, обычный буфер ОС (87040 при старте) | 58,1–92,7 | 343–496 |

Все 18 коротких передач завершились полным 413. Nagle не установлен как причина; размер клиентского буфера влияет. В pcap медленных передач есть повторные TCP sequence; нулевые окна встречаются и у быстрой 7″, поэтому сам факт zero-window не доказывает дефект. Значимых различий SDK Wi-Fi/lwIP/CPU/FreeRTOS/PSRAM config между профилями не найдено. Физическое расположение/антенны и b43 не переставлялись; радиопричина разницы пока не установлена.

По захвату 4,3″ новый Rescan: idle 49/49 ICMP, во время сценариев 371/271 (~27% потерь); beacon-loss в окне этой серии нет. На 7″ в первой новой серии idle 49/49, сценарии 240/185 (~23%), четыре beacon-loss, без потери association. Группировка не обещает отсутствия любых потерь при переключении каналов. Для сравнения старой 7″ ~47% потерь во время сценариев; объём серий отличается, это не лабораторная оценка вероятности отказа. В общей временной выборке ещё 17 beacon-loss относились к домашней Meotida, не к Aura.

На обеих платах реально прошли четыре TCP-бёрста по 64 КиБ с тремя паузами по 2,2 с: полный HTTP 413 за 9,54 с (4,3″) и 7,13 с (7″). Остановившийся отправитель освободил сервер для следующего клиента через 5,10 и 5,03 с соответственно. Полный 3,39-МиБ native-buffer контроль 4,3″: 2/3, успешные 69,7–71,7 с; одна потеря ответа из-за 5-секундного progress_timeout после ~3,04 МБ на устройстве. Увеличенное окно не обещает сохранения ответа при произвольно долгой потере радио.

Пользователь подтвердил: обе платы стоят рядом, условия примерно одинаковые; 4,3″ была медленнее и до доработок. Это усиливает необходимость отделять аппаратную/радиочасть от регрессии HTTP, но не устанавливает конкретную причину.

## Android, восстановление и окончательный статус

Android 7″: 15/15 API-сценариев ON/OFF/wake, все с наблюдаемым scan. По 3/3 полных страниц, 413 oversized-settings и 400 + JSON INVALID_SIZE для OTA без ota_size. OTA written=0/rebooting=false, физическое разрешение OTA не обходилось. Curl читает ранний ответ и прекращает тело: size_upload около 1–1,3 МБ при файле 3,39 МБ. Его reported speed_upload характеризует локальную передачу в буферы, не полный радио-goodput; эти числа не используются как скорость прошивки.

Свежие подключения Android 7″ через ADB и через обычное меню Wi-Fi НЕ показали автоматический captive portal. Актуальный validation log: DNS OK 192.168.4.1, HTTPS connect refused, затем `DNS response to the URL is private IP`; HTTP probe пропущен. Это соответствует [AOSP NetworkMonitor](https://android.googlesource.com/platform/packages/modules/NetworkStack/+/refs/heads/main/src/com/android/server/connectivity/NetworkMonitor.java): опциональная private-IP логика прекращает captive detection. Гипотеза о причине в ADB-подключении не подтвердилась обычным UI-подключением. Ранний успешный CNA на 4″ с уже существовавшим сетевым состоянием не доказывает свежий автоматический вход.

После штатного выбора Android «Connect only this time» обычный curl и Chrome по http://192.168.4.1/wifi получили полный 200 при mobile_data=1. Настройки Android captive_portal/private_dns не менялись. Обещание универсального auto-popup не допускается. DHCP option 114 рассмотрена: [официальный Android CAPPORT](https://developer.android.com/about/versions/11/features/captive-portal) требует API, а AOSP допускает для него HTTPS; простая HTML/HTTP URI из примера SDK не решает этот контроль. TLS/certificate infrastructure не добавлялась.

Android 7″: ещё 3/3 реальных нажатия Rescan в Chrome с наблюдением scan и возвратом списка; через обычную форму получена страница Settings sent, затем устройство обнаружено в STA. Материалы: `phone/radio-chrome-rescan-7/`, `phone/radio-save-7/`.

Android 4,3″ НЕ получил такой же результат:

- `radio-matrix-4`: три ON-сценария прошли, четвёртый не завершил проверку. Старое сообщение стенда «scan did not finish» не отличало ненаблюдённый старт; одновременно происходила навигация Chrome. Это не доказанный зависший драйвер.
- `radio-matrix-4-observed`: повтор остановился до сценариев — второй `/api/diag` не закончил тело за 12 с (4225 из 5199 байт). `radio-matrix-4-traced`: полная scan-страница пришла за 5,86 с; все полученные статусы были false, затем отдельный запрос достиг 12-секундного таймаута. Активный scan не наблюдался. OFF/wake на этом телефоне/профиле не покрыты; успешный Mac-прогон их не заменяет.
- `radio-chrome-rescan-4` не начал тест: передним приложением были Settings. После вывода Chrome `radio-chrome-rescan-4-visible` подтвердил первый Rescan за 7,06 с; во втором увидел активный scan/Scanning, но не подтвердил список за 26,61 с. Последний accessibility dump содержал только оболочку Chrome. Более поздний screenshot `after.png` показывает полный список сетей, поэтому пустой dump НЕ доказывает пустой экран или зависание прошивки. Третий Rescan не выполнялся.
- `radio-http-4` остановился на неполном preflight JSON, до тестов. В `radio-http-4-visible` получены три полных страницы HTTP 200 (0,63–8,46 с) и один полный 413; затем контрольный `/api/diag` завершился ошибкой проверки результата. Уточнение после независимого ревью: 100 с были заданным лимитом curl, а не измеренным временем; traceback уже записан в 13:36:58 UTC. Подробные exit/stderr этого запроса не сохранены. AP-ответ 400 OTA на 4,3″ в этой серии не проверен. Эти остановки сохранены, а не исключены из отчёта.
- `radio-save-4`: обычная форма Chrome применила домашнюю сеть, serial и Mac подтвердили STA 192.168.88.54. Chrome вместо подтверждения показал Connection timed out на `/save`. Полное получение HTML не подтверждено. Это новая неуспешная аппаратная попытка поверх прежнего исправления grace после scan; считать `/save` универсально исправленным нельзя. Причина потери (TCP-доставка перед выключением AP, клиентский маршрут или иной фактор) не изолирована.

В serial 4,3″ один `HTTP interrupted` был раньше этих матриц: path `/`, User-Agent Dalvik, connection_reset после 13140/26488 байт, scan=false. Это закрытие со стороны TCP-peer, а не само по себе доказательство зависания HTTP server или причина Chris. Нельзя приписывать его последующему Chrome Rescan. В собранных serial нет panic/heap corruption/stack overflow/WDT.

## Контроль через домашний роутер

Тот же Mac, TCP_NODELAY, обычный send buffer ОС, по три полных передачи 512 КиБ:

| --- | --- | --- |
| SoftAP, канал 1 | 58,1–92,7 | 343–496 |
| STA через Meotida, канал 6 | 117–224 | 392–512 |

Все короткие STA-передачи завершились полным 413. Полные 3 393 552 байта на 4,3″ через роутер: 3/3, 24,33–25,01 с, 132–136 КиБ/с (`4_3/radio-sta-full/`). По сравнению с SoftAP меняются также канал, AP-радио и сетевой путь; это НЕ изоляция только программного режима.

Android через роутер на 4,3″: 3/3 oversized 413, 3/3 OTA 400 с INVALID_SIZE, written=0/rebooting=false, следующий API работал (`phone/radio-http-4-sta/`). Три `/wifi` дали штатный 404: маршрут доступен в AP. В отдельном контроле правильного `/dashboard` с `curl --compressed` все три полных HTML 200 получены за 0,095–0,211 с (`radio-sta-pages-4-decoded/`). Первая попытка декодировать gzip как UTF-8 была ошибкой стенда, не устройства. Ранние ответы curl прекращают отправку тела, поэтому их speed_upload не используется как радио-скорость; следующий клиент может ждать дочитывания уже буферизованных данных.

Вывод по скорости: разница между этими двумя экземплярами сохраняется и в STA, а SoftAP дополнительно ухудшает 4,3″. Данные совместимы с особенностями платы/антенны/помех/взаимодействия с клиентом, но аппаратная причина не доказана. Само прежнее отличие скорости не делает нормальными таймауты небольших страниц. Конфигурация SDK, выключение экрана, Nagle и увеличение клиентского буфера не объяснили всю разницу. A/B с другой платой 4,3″, одинаковым каналом и контролем питания/антенны не проводился.

## Финальное восстановление и следующие границы

- 4,3″ оставлена на `0ea63f716d55…`, как разрешил пользователь.
