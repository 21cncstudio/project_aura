# AP/HTTP: постоянные проверки владения, 2026-11-01

Четыре пробела покрытия из [третьего независимого ревью](HTTP_AP_REPAIR3_RECHECK_20261101.md) закрыты постоянными сценариями S29–S32. Они включены в обычный полный SDK-прогон. Добавлена воспроизводимая проверка четырёх намеренных откатов в отдельных копиях. Все проверки прошли. Обе команды инкрементальной сборки завершились успешно; Ninja использовал готовые артефакты без перекомпиляции и линковки.

Производственный код не менялся. После инкрементальной проверки сохранились те же BIN третьей доработки; SHA256 всех 24 артефактов совпали с сохранёнными файлами. Это проверка сохранности и актуальности входов Ninja, не новая чистая сборка. Это укрепляет тестовое покрытие того же кандидата, не меняет его сетевые ограничения и не заменяет аппаратную приёмку. Причина жалоб Chris/#158 остаётся неизвестной.

Работа выполнена на main, база `77bfb4b0209a57c4a511352743cd7eb55a385df1`, изменения незакоммичены. Устройства, COM, прошивка, публикация, commit/push и Hub не затрагивались.

## Что добавлено

| Постоянный сценарий | Что именно ломает намеренный откат |
| --- | --- |
| S29, порт A26 | Без проверки живого lease stop вызывается в Switching, хотя worker ещё не получил admission. |
| S30, порт A27 | Ранний release разрешает wake, пока драйвер ещё очищает результаты scan. |
| S31, порт A28 | Без mutex worker выполняет cleanup и освобождает lease, пока SDK stop ещё не вернулся. |
| S32, усиленный Z10 | Без повторного acquire HTTP продолжает drain без lease между двумя wake; JSON при этом может оставаться полным. |

S29 удерживает worker перед выполнением его функции. S30/S31 ставят управляемый барьер внутри SDK-заглушки: проверяется реальное владение во время незавершённого вызова, а не предположение о длительности 350 мс. В S31 сетевым владельцем является один отдельный поток; основной поток моделирует wake и не вызывает poll/cancel параллельно. S32 ждёт фактического half-close перед первым wake, проверяет повторный lease, отсутствие I/O в защищённых фазах, полный JSON и следующий клиент.

Это проверки production WifiScanSession, WakePowerGuard и HTTP transport в существующем SDK-стенде. NetworkManager/NetworkPlane и настоящая очередь команд здесь не исполняются. Отдельный manager-стенд 138/138 сохранён в материалах предыдущей сверки; в постоянный набор перенесены именно четыре инварианта, а не все его 29 сценариев.

## Воспроизведение и доказательства

```powershell
python -X utf8 tools/test_http_server_sdk.py --idf-path D:/21cncstudio/project_aura_aq/tools/idf61-sdk/esp-idf
python -X utf8 tools/test_http_guard_mutations.py --idf-path D:/21cncstudio/project_aura_aq/tools/idf61-sdk/esp-idf
```

Новый mutation runner сначала запускает исправный контроль, затем правит по одному месту в отдельных копиях. Успех требует конкретного сообщения FAIL и ожидаемого кода тестового процесса. Ошибка компиляции, timeout, отсутствие result.json или посторонний FAIL не засчитываются. Исходники основной рабочей копии сверяются после прогона. Выходной каталог должен быть новым; старые результаты не удаляются. Подробности: [README стенда](../test/support/http_server/README.md).

Доказательства: `build/http-ap-coverage-20261101/`:

- `targeted/`, `sdk-full/`, `sdk-full.log`: отдельный и полный SDK-прогоны, команды и source hashes.
- `mutations-verified/result.json`, подпапки control и четырёх откатов: команды, исходники, точечные изменения и ожидаемые FAIL.
- `native.log`, `native-reports/`, `tcp/`: остальная валидация.
- `build-4_3.log`, `build-7_dual_i2c.log`, `build-artifact-verification.json`: обе инкрементальные команды и сверка 24 артефактов. Идентичные бинарники повторно не дублировались; точные сохранённые файлы указаны в JSON.
- `before/`, `final-source/`, `local-scripts/`, `validation-summary.json`: исходная точка, итоговый снимок и проверка неизменности production source.

## Что остаётся

Сетевые лимиты не изменены: 90 с/8 МиБ и прогресс 32 КиБ за 1500 мс. Для проверенного размера 40 КиБ/с проходит, 36 нет; пауза 1,4 с проходит, 1,7 нет. Повторы браузера могут занять больше одного 90-секундного budget. Гарантированного дедлайна wake на ESP32 нет.

Следующий этап — отдельно разрешённая аппаратная матрица точных BIN: SoftAP/телефоны, медленное радио и паузы, wake при reject и scan, OFF/forget/AP→STA, restart/factory reset во время scan, первый AP boot, stack worker 4 КиБ и длительный прогон обоих профилей. Кандидаты готовы к этой проверке; готовность к выпуску пока не установлена.
