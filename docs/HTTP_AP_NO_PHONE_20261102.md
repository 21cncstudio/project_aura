# AP/HTTP: доработка и аппаратная проверка без телефона, 2026-11-02

Кодовые дефекты исправлены и защищены тестами. Выпуск не разрешён: новая телефонная матрица ещё не выполнена, а изменение частоты дисплея требует проверки изображения и плавности на устройстве. Причина исходных жалоб Chris/#158 не установлена.

Исправления кода и постоянные тесты сохранены локальным коммитом `e89699b6`. Исходная база — main `1ab69d03`. Разрешены обе платы с возвратом 7″ на исходный Hub; 4,3″ можно оставить на новом кандидате с исходными настройками. Все сетевые аппаратные тесты шли через MacBook `aura-ha-lab` (Ubuntu, BCM4331/b43), не через Windows Wi-Fi. Host-тесты Windows — отдельные проверки кода/SDK, не радио.

## Исправления

- Scan в AUTO пассивно слушает вне активного country-диапазона до 14 канала; MANUAL остаётся внутри своего диапазона. Между каналами сохраняются 120 мс дома и activity lease. A38/A44 усилены для lease/mutex, A43/A45/A46 проверяют AUTO/passive/MANUAL.
- `/save` сначала сохраняет настройки и отдаёт страницу со случайным receipt. Только полный успешный stream вооружает receipt; только обратный запрос загруженной страницы разрешает переход AP→STA. JavaScript делает его после `window.load`, без JavaScript есть кнопка. Сохраняются ожидание завершения scan и grace 200 мс. Receipt живёт 10 минут, отменяется новым save/закрытием AP; повтор не запускает второй переход. Старым прямым HTTP-клиентам теперь нужен `/wifi/confirm`. Уже сохранённые настройки могут примениться при перезапуске даже без receipt.
- Неудачный обычный `send()` через HTTP handlers попадает в ограниченную историю `web_stream`: SDK error, валидный errno, частичные body bytes, path без query, peer/UA и окружение. Это не обещает охват всех внутренних отказов транспорта и не считает локальный send доказательством доставки.
- Общий drain увеличен с 90 до 120 с после реальных отказов 4,3″ на 34–36 КиБ/с. Независимые 8 МиБ и 32 КиБ/5000 мс сохранены, wake по-прежнему получает возможность остановить drain. Это предел одной попытки; браузер может повторить запрос. Ожидание безопасного admission может увеличить фактическое время закрытия, FailClosed не открывается ради таймера.

TCP FIN закрывает одно направление, а принятие данных SDK ещё не подтверждает загрузку страницы клиентом ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6.1)). Поэтому выбрано прикладное подтверждение. Country semantics сверены с [ESP-IDF Wi-Fi guide](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-guides/wifi-driver/overview.html#wi-fi-country-code). Готового receipt-механизма в прежних Aura/Hub путях нет.

## Аппаратные результаты

- Rescan: **9/9 на каждой плате** — по три screen on/off/software wake. Полные страницы, наблюдённый scan и завершение. Это не физическое касание экрана.
- AUTO scan каналов вне активных 1–11: **3/3** на 4,3″ нашли отдельную AP на реальном канале 13. В read-only диагностике подтверждены world-safe `01/AUTO/1..11`; на второй плате — `DE/MANUAL`, фактический канал 13. Scan source совпадает с основным кандидатом.
- Chromium на Mac: реальная форма `/wifi`, полный `/save` во время наблюдённого scan, автоматический receipt и последующий домашний STA — обе платы. Без JavaScript обе остаются в AP до нажатия кнопки; после неё STA подтверждён.
- Полная страница без receipt, неправильный receipt, TCP reset до получения страницы и устаревший receipt — AP сохраняется. На 7″ десять последовательных циклов дали **40/40**.
- На 7″ с новым drain: **3/3** полных 413 (347–399 КиБ/с) и **3/3** OTA 400 (376–406 КиБ/с). OTA-тест намеренно не передаёт `ota_size`, результат `INVALID_SIZE`, `written=0`, `rebooting=false`: это доставка раннего отказа, не проверка hardware identity и не обход физического разрешения OTA.
- Recovery 7″: полный ответ после повторных пауз отправителя по 2,2 с; следующий клиент после остановившегося отправителя примерно через 5,10 с. **2/2**.
- Эти полные AP-сценарии 7″ проведены до исправления отдельного MQTT forwarding; AP/HTTP пути с того момента не менялись. На точном окончательном BIN повторно проверены build/profile/STA, JSON, целый gzip HTML, HEAD 405 без тела, отказ confirm в STA и отсутствие диагностического endpoint: **8/8**.

На точном окончательном BIN 4,3″ (`6b458247…`, PCLK 16 МГц):

- **3/3** полных 413, 3 403 060 байт за 33,02–42,65 с (77,93–100,65 КиБ/с).
- **3/3** полных OTA 400/JSON, `INVALID_SIZE`, `written=0`, `rebooting=false`, 33,84–38,94 с (85,34–98,21 КиБ/с).
- **2/2 recovery**: повторные паузы по 2,2 с не потеряли полный 413; после остановившегося отправителя следующий клиент получил HTTP 200 через 5,04 с.
- **40/40** в десяти циклах no-receipt/bad receipt/TCP reset/stale receipt.

В этой серии скорость выше ранних 34–40 КиБ/с, но всё ещё ниже 7″ и низких PCLK. Разница условий по времени не позволяет объявить timer fix причиной ускорения. Дополнительно на этой же плате при ограничении отправителя до **32 КиБ/с** полный файл получил 413 за **103,854 с**, а полный OTA POST получил 400/JSON за **103,854 с**: **2/2**. Тем самым новый предел проверен на радио/lwIP после пересечения прежних 90 с, а не только на host-стенде.

## Почему медленнее 4,3″ и что даёт снижение PCLK

На минимальном Wi-Fi-only образе без Arduino/LCD/UI/датчиков обе платы значительно быстрее: 4,3″ 561–618 КиБ/с, 7″ 638–671 КиБ/с. В обоих случаях по три полных POST и около 4 мс idle RTT, 48/50 ping. 318 параметров SDK совпадают; handler paths и наличие второй AP в этих опытах различаются. Это контроль runtime, не точный аппаратный benchmark.

Пауза LVGL при продолжающемся RGB DMA не улучшила скорость. PS MIN/NONE/MIN также не устранил задержку; power save Mac всё время был off. На одном диагностическом BIN с PS_NONE смена RGB PCLK 16→8→16 МГц дала 165–203→344–587→70–100 КиБ/с, RTT 14,9→2,38→24,6 мс; callbacks подтвердили 39→19,5→39 Гц. Значит, зависимость от дисплейного тракта есть. PSRAM/DMA contention и радиопомехи этим опытом не разделены.

По дополнительному запросу владельца проверены ещё более низкие частоты. Один BIN, одна плата, PS_MIN как у основной прошивки, Mac power save off, по два полных файла 3 403 060 байт на фазу; после каждого низкого значения возвращались к 12 МГц. Последовательность 12→8→12→6→12→4→12, **14/14 полных HTTP 413**:

| PCLK | Передач | Скорость, КиБ/с | Медиана, КиБ/с | Реальные refresh callbacks/с |
| --- | ---: | ---: | ---: | ---: |
| 12 МГц | 8 | 292–441 | 419 | 29,25–29,30 |
| 8 МГц | 2 | 423–440 | 431 | 19,51 |
| 6 МГц | 2 | 485–509 | 497 | 14,65 |
| 4 МГц | 2 | 287–449 | 368 | 9,75 |

Ниже 12 МГц нет монотонного улучшения. На 8 почти тот же результат; на 6 около 19% выше медианы 12, но обновление дисплея вдвое реже; на 4 результат хуже. Выборка мала, условия по времени меняются: это не обещание скорости для других клиентов. Ошибок display sync/роста framebuffer wait timeout в этой серии нет, но само изображение и плавность глазами не проверены.

**Предложение — 12 МГц только для 4,3″ как следующий кандидат**, не постоянное снижение до 6/4. Патч `proposal-4_3-pclk12.patch` подготовлен и не применён к main. Нужны визуальная проверка и повтор scan/wake/phone на выбранной частоте. Процессор не замедлялся. SDK предоставляет штатное изменение PCLK на следующем VSYNC ([RGB LCD API](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/lcd/rgb_lcd.html)); [LCD FAQ](https://docs.espressif.com/projects/esp-faq/en/latest/software-framework/peripherals/lcd.html) и [Wi-Fi performance guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/wifi-driver/wifi-performance-and-power-save.html) объясняют возможные ограничения, но не доказывают конкретную причину на этой плате.

## Неудачные попытки и ограничения

- При старом drain 90 с полный отказ на 4,3″ прошёл только **1/3**: два time_limit при 34,3/35,7 КиБ/с. Именно это обосновало 120 с; причина низкой скорости не объявляется исправленной увеличением таймера.
- Один ранний RST-сценарий 7″ дал timeout следующего запроса. Повтор с фазовым журналом и 40 проверок его не повторили; причина не установлена.
- Один DNS UDP timeout на 7″ остановил сценарий до upload, хотя `/api/diag` перед ним прошёл за 40 мс. Runner теперь записывает до трёх независимых попыток; следующий тест ответил с первой за 5 мс. Это не доказательство отсутствия UDP-потерь.
- Первые browser/health fixtures были неверны: запрещённый `file://` заменён локальным HTTP handoff; составной no-JS Playwright вызов разделён; STA `/wifi` ожидаемо 404, dashboard gzip, HEAD ожидаемо 405. Исходные ошибки сохранены, не приписаны firmware.
- Первый preflight 7″ не успел получить маршрут; отдельный повтор на установленной связи успешен.
- Первый SDK fixture превысил настоящий лимит 48 routes; регистрация ограничена текущим сценарием, лимит firmware не повышали. Параллельные mutation servers конфликтовали портом; повторены последовательно. S35 усилен вторым poll, иначе он не ловил неверно начатый grace. Неуспешные сборки wiring-стенда и запуск с отсутствующим context не считаются проверкой firmware.
- Телефон сейчас не участвовал. Android 4,3″ требуется повторить полностью; iOS, физические касания, реальные OFF/ON не покрыты. Windows AX211 не перепроверялся по прямой инструкции использовать Mac. Автоматический popup Samsung на private AP IP остаётся отдельным вопросом; чужой публичный IP в production не вводился.
